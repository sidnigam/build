# Phase 05.3 Plan 03: Scheduler, Stingers, AUDIO Integration & Audition Hook Summary

**The procedural Hindustani score now actually plays: a 25ms lookahead scheduler drives tala-quantized intensity transitions and raga crossfades, eight D-07 stingers fire on state transitions, `AUDIO.init()` wires it all to the live game (legacy sawtooth drone deleted, clashing tonal SFX replaced in-key), and a hidden debug hook plus a 4-raga/level-5 CPU soak prove the budget.**

## Performance

- **Duration:** ~4h
- **Tasks:** 3 completed
- **Files modified:** 4

## Accomplishments

- **Scheduler (Task 1):** `MUSIC.start/stop/_loop/_tick/_scheduleStep` — a 25ms `setTimeout` lookahead loop with a 0.12s schedule-ahead window, polling `logic.snapshot(GAME)` -> `deriveTarget` -> a hysteresis governor every tick. Level increases apply at the next vibhag; decreases require >=3s held then land on the next sam (or a vibhag if the sam is >4s away). Raga changes (biome switch, hub return) fade all stems to 0 over 1.2s, swap the raga/bank/lead-stream, and restart at step 0. Tempo glides at <=2bpm/step. The tanpura runs in free time (not tala-locked) and its cursor keeps advancing (silently) while muted, so it re-syncs on unmute without a catch-up burst. Re-priming after a real-time gap (e.g. a backgrounded tab) avoids a scheduling burst.
- **Stingers + AUDIO integration (Task 2):** all eight D-07 stingers (`bossIntro`, `bossPhase`, `roomClear`, `bossDefeated`, `reward`, `revive`, `death`, `victory`) implemented via a two-lane queue (`freeQueue` for immediate hits, `stepQueue` for tala-exact tihai/pickup landings). `AUDIO.init()` now attaches and starts `MUSIC` automatically; `startDrone`/`stopDrone` are thin `MUSIC.hint()` shims (the legacy detuned-sawtooth drone builder and `musicNodes` field are gone); `AUDIO.sfx()` skips `death`/`victory`/`roomclear`/`boon`/`defiance` while `MUSIC.isAudible()` so the in-key music cue plays instead, and falls back to the old chime the instant music is silenced. `musicDynamics` (D-13) caps the intensity level for accessibility/ear-fatigue. The hidden debug/audition hook (`MUSIC.debug`/`debugStinger` + Backquote-held key chords) lets a human audition any raga x level x stinger instantly.
- **Stress/budget + variety (Task 3):** a 120-simulated-second, level-5 (densest texture) soak per biome raga confirms `stats.avgTickMs` stays at ~0.002ms — roughly 350x under the 0.75ms (3% of the 25ms tick) budget — with `peakActive` never exceeding the 28-voice cap and fewer than 50 audio nodes created per simulated second. A 64-cycle bhairav run at level 2 produced 29 distinct 5-note phrase-degree windows, confirming the generator's novelty logic produces real melodic variation rather than looping.
- 216 additional automated checks (bringing the suite to 973 total across all of Phase 05.3) — `node test/smoke.js` verified green across 10+ consecutive runs (deterministic; see Deviations for why that mattered).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `MUSIC.leadNote` scheduled two frequency automation events at the identical ctx time**
- **Found during:** Task 1 (the "lead never double-books a ctx time" scheduler smoke check, with a fixed test seed)
- **Issue:** `genPhraseNotes` (05.3-01) can independently set both `glide: true` and `orn: 'murki'` on the same note. The 05.3-02 `leadNote()` implementation ran the glide branch's `setValueAtTime(prevHz, t)` and then, separately, the murki block's `setValueAtTime(upperHz, t)` — two writes at the exact same `t`, silently overwriting each other and leaving the glide's ramp target still queued to fire mid-turn.
- **Fix:** Made murki mutually exclusive with kan/glide's onset write (murki now owns the full pitch envelope for the note when present, since a quick turn stands in fine for a meend/kan on that same note).
- **Files modified:** `js/music.js`
- **Commit:** `c86af15`

**2. [Rule 1 - Bug] Governor down-hold hysteresis dt sourced from wall-clock instead of the ctx clock**
- **Found during:** Task 2 (the "victory eventually settles to level 1" integration check, after the death->victory sequence)
- **Issue:** `_tick()` computed `dt` from `performance.now()` deltas between ticks. That's correct for a real `setTimeout(...,25)` loop (wall time and ctx time move together), but the test harness pumps many ticks back-to-back while only advancing a mock `AudioContext` clock — real elapsed CPU time per tick is near-zero, so the governor's 3-second down-hold could never accumulate, and the level never actually dropped in tests (a latent bug that happened to not be exercised by Task 1's own down-hold test, which passed by coincidence of incidental CPU cost inside the vm sandbox rather than correct logic).
- **Fix:** `dt` is now `ctx.currentTime` deltas (simulated/game time), which is correct in both real play (ctx.currentTime tracks wall time for a live `AudioContext`) and in tests (fully controlled by `mock.advance()`).
- **Files modified:** `js/music.js`
- **Commit:** `e9b5832`

### Test-only fixes (no production-intent change)

- `MUSIC.start()` gained an optional `seed` parameter used only by tests, so scheduler/stinger/stress smoke checks are fully deterministic (verified green across 10+ consecutive runs) instead of depending on `Date.now()`. Production's only caller (`AUDIO.init()`) always omits it, so real gameplay still gets a fresh per-run seed per D-09.
- Two 05.3-02 "MUSIC engine (mock AudioContext)" assertions (`attach returns true the first time` / node-count-after-attach) were updated to reflect that `AUDIO.init()` now auto-attaches+starts `MUSIC` itself — the old assertions tested a call sequence (`AUDIO.init()` then a separate manual `MUSIC.attach(AUDIO)` expected to be the *first* attach) that this plan's own integration change made stale.

## Debug / Audition Guide

1. Launch the game (`npm run start:desktop`, or open `index.html?musicdebug` directly in a Chromium-based browser) and open DevTools (Cmd+Opt+I). Click once anywhere in the page to unlock the AudioContext (first-gesture policy).
2. From the console:
   - `MUSIC.debug(level, ragaOrBiomeId)` — force an intensity level (0-5) and/or a raga. Accepts either a raga id (`'yaman'|'bhairav'|'malkauns'|'adana'|'bhairavi'`) or a biome id (`'hub'|'naraka'|'patala'|'ranabhoomi'|'vaitarani'`). Crossfades in ~1.2s like a real biome change.
   - `MUSIC.debug(null)` — clear the override and return to following the real game state.
   - `MUSIC.debug()` — returns `{ ragaId, level, bpm, section, stats }` (current state + perf counters).
   - `MUSIC.debugStinger('bossIntro'|'bossPhase'|'roomClear'|'bossDefeated'|'reward'|'revive'|'death'|'victory')` — fire one stinger on demand.
   - `SETTINGS.set('musicDynamics', 0..1)` — cap the intensity ceiling (0 = always calm; 1 = default, full range).
3. Key chords (hold Backquote `` ` `` and press, once debug mode is active — either via the URL flag or after the first `MUSIC.debug(...)` call):
   - `0`-`5` — force that intensity level
   - `B` — cycle through the five ragas
   - `S` — cycle through and fire the eight stingers
   - `X` — clear the debug override
   - `P` — print `MUSIC.stats` to the console
4. Tuning knobs, if a mix pass is ever needed: `MUSIC.MIX` (per-stem gain), `MUSIC.OUTPUT_TRIM`, `MUSIC.theory.INTENSITY` (per-level stem-gain table), `MUSIC.theory.LEAD_PRESETS` (lead-instrument timbre/vibrato), `MUSIC.theory.RAGAS[*].bpm` (per-raga tempo).
