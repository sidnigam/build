## Summary

The current `js/audio.js` already has the right foundation: a tanpura-style drone (`startDrone(rootHz)`) keyed to each biome's `droneHz` in `js/data.js`, a `musicGain` node wired to `SETTINGS.musicVolume`, and a pure-synthesis SFX vocabulary with correct click-free envelope shaping (`setValueAtTime` → `exponentialRampToValueAtTime`, never a hard cut). The gap is: no rhythm layer, no melodic layer, and no intensity-driven adaptation — `startDrone` is called once per biome entry (`js/rooms.js:356`) and never changes again.

**Primary recommendation:** Build the score as **fully procedural Web Audio synthesis** (Karplus-Strong-style plucked-string model for tanpura/sitar-ish lead, pitched noise-burst + resonant-filter membrane model for tabla/dhol, sine-cluster physical-ish model for bansuri/shehnai), organized as 4-5 gain-automated stems (drone, rhythm, melody, percussion-intense, riser) driven by a lookahead scheduler, with raga-constrained melody generation and tala-based bol scheduling per biome. This has zero licensing risk, zero file-size cost, and composes naturally with the existing `AUDIO` object's null-safety pattern. CC0 one-shot samples are a viable *later* enhancement for texture (see below) but are not required and no clean CC0 Indian-instrument library actually exists today (verified — see Sources), so don't block the phase on sourcing them.

## Standard Stack

### Core
No new dependencies. Everything below runs on the native Web Audio API already used by `js/audio.js`.

| Component | Purpose | Why |
|---|---|---|
| `OscillatorNode` + delay-line feedback (custom, or `ScriptProcessorNode`/`AudioWorkletNode`) | Karplus-Strong plucked string (tanpura resonance, sitar-ish lead) | No native "plucked string" node exists; KS is the standard cheap physical-ish model, well documented, works in plain Web Audio. |
| `AudioBufferSourceNode` + `BiquadFilterNode` (bandpass) | Tabla/dhol/mridangam pitched membrane hits | Same technique already used for `AUDIO.noise()` SFX — a short noise burst through a resonant bandpass with fast decay reads as a struck drum. Proven in-engine already. |
| `GainNode` per stem + `AudioParam` automation (`linearRampToValueAtTime`) | Intensity crossfades between layers | Native, zero-cost, exactly the pattern `_applyVolumes()` already uses. |
| `AudioWorkletNode` (optional, Electron/Chromium only) | Higher-fidelity Karplus-Strong loop if `ScriptProcessorNode` (deprecated) proves too CPU-heavy | Electron's bundled Chromium fully supports AudioWorklet; safe to use since there's no browser-compat constraint (Steam desktop only). |

## Architecture Patterns

### Recommended structure (new file `js/music.js`, loaded after `audio.js`, before `data.js` per smoke.js's load order convention)

```
js/
├── audio.js        # existing: SFX, drone (keep as-is, or fold drone into music.js)
├── music.js         # NEW: MUSIC global
│   ├── MUSIC.patterns   # PURE, ctx-free: scales, pakad phrase banks, tala bol arrays,
│   │                    # intensity->layer-gain tables. Smoke-testable without AudioContext.
│   ├── MUSIC.voices     # ctx-touching synthesis: pluckString(), membraneHit(), leadTone()
│   ├── MUSIC.scheduler  # lookahead loop, bar/beat counters, stem gain automation
│   └── MUSIC.state      # current biome, current intensity level, current bar/beat
```

Keep `MUSIC.patterns` free of any `this.ctx` reference — pure functions/data (scale degree arrays, bol strings, phrase-length ints). This is what lets `test/smoke.js` assert "Naraka's tala has 16 steps" or "intensity 3 sets percussion gain to X" without a real `AudioContext`, matching the project's existing headless-safe pattern (`SETTINGS`, `AUDIO.setVolume` already guard `ctx`/`STORE` this way).

### Pattern 1: Lookahead scheduler (the standard Web Audio timing pattern)
**What:** A `setTimeout` loop firing every ~25ms that looks `scheduleAheadTime` (~150-200ms) into the future and schedules exact note-start times using `ctx.currentTime`, not the timer's own firing time.
**When to use:** Any Web Audio sequencer — this is the only reliable way to avoid setTimeout jitter causing audible timing drift. (This is the "A Tale of Two Clocks" pattern popularized by Chris Wilson's canonical Web Audio scheduling article — HIGH confidence, this is the field-standard approach, not a novel technique.)
**Example (adapted to bols/tala):**
```javascript
// MUSIC.scheduler — 25ms lookahead, 150ms schedule-ahead window
_tick() {
  while (this.nextStepTime < this.ctx.currentTime + 0.15) {
    this._scheduleStep(this.currentStep, this.nextStepTime);
    const secondsPerBol = 60 / this.tempo / 4; // 16th-note grid under current tala
    this.nextStepTime += secondsPerBol;
    this.currentStep = (this.currentStep + 1) % this.tala.length;
    if (this.currentStep === 0) this._onBarBoundary(); // tihai / crossfade check
  }
  this._timerId = setTimeout(() => this._tick(), 25);
}
```

### Pattern 2: Bar-quantized intensity transitions
**What:** Never change stem gains or swap the tala/theka mid-cycle. Compute the target intensity every frame from game state, but only *apply* the gain ramp at the next `sam` (beat 1) via the scheduler's bar-boundary hook.
**When to use:** All layer add/remove events (entering combat, boss phase 2, low HP) — prevents the jarring "rhythm restarts on a random beat" artifact.

### Pattern 3: Tihai cadence as a reward stinger
**What:** A short melodic/rhythmic phrase repeated exactly 3 times, landing precisely on the next bar's beat 1 (`sam`) — the traditional Hindustani/Carnatic cadential device.
**When to use:** Room-clear (`this.state === 'cleared'`), boss-kill. Schedule it the moment the trigger fires, but compute its start time so the 3rd repeat's final note lands on the next tala cycle's beat 1 — gives a satisfying, idiomatically-correct "landing."

### Suggested intensity levels (drive from existing `GAME.state` + boss/HP signals already in `js/game.js`)
| Level | Trigger (from `game.js`) | Layers active |
|---|---|---|
| 0 — Hub | `state === 'hub'` | Drone only, slow shimmer, Yaman-flavored calm phrase, no percussion |
| 1 — Explore | `state === 'cleared'` or empty room | Drone + sparse melody (long note values), theka at half tempo |
| 2 — Combat | `state === 'combat' && !bossRef` | Drone + theka at full tempo + melody phrases |
| 3 — Low HP | combat + `player.hp / player.maxhp < ~0.3` (mirror existing low-HP checks in `game.js`) | Add dissonant drone stab layer (tivra/komal clash), density up |
| 4 — Boss | `bossRef` set | Full percussion (laggi subdivisions), riser stems on phase transitions, faster tala variant |
| 5 — Boss phase 2 | boss HP threshold (pattern already exists for boss phases per `bossRef`/`bossHurtT`) | Double-time jhala-style melody, dhol/taiko hits doubled |

### Anti-Patterns to Avoid
- **Restarting the whole drone/rhythm graph on every intensity change:** causes clicks and phase resets. Instead, ramp existing stem gains; only tear down/rebuild nodes when biome (root pitch/raga) actually changes.
- **Driving note timing off `requestAnimationFrame`:** rAF is throttled when the Electron window loses focus; the audio scheduler must run on its own `setTimeout` loop independent of the render loop (see Pitfalls).
- **One `AudioBufferSourceNode`/`OscillatorNode` "held and restarted" per hit:** both node types are single-use per spec (`start()` can only be called once, ever) — plan for "cheap node per note, reused `AudioBuffer`/reused bus `GainNode`," not literal node pooling.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Audio-accurate timing | A `setInterval`-only sequencer | Lookahead scheduler (Pattern 1) | `setInterval`/`setTimeout` alone drift by 10s of ms under load; audio needs sample-accurate `start(time)` calls, timer only needs to be "close enough, early enough." |
| Plucked-string timbre | A single detuned sawtooth (current drone approach, functional but thin) | Karplus-Strong delay-line pluck | A single filtered sawtooth cannot produce the characteristic tanpura/sitar decay-and-buzz; KS is the standard cheap trick and is a delay line + lowpass + feedback gain — small amount of new code, big timbral win. |
| Drum membrane sound | Layering more sine oscillators | Noise burst + tuned bandpass + fast exponential decay (same technique as existing `AUDIO.noise()`) | Already proven in this exact codebase for SFX; extend the pattern rather than inventing a new one. |

**Key insight:** Nothing here needs a new library or file-based asset — it's all extensions of techniques already present in `js/audio.js` (`tone()`, `noise()`, drone's LFO-shimmer gain). The phase is additive, not a rewrite.

**"Intense modern" layer (Baahubali/RRR-style fusion, applied at intensity 4-5):**
- A sustained low sine/sub drone (~40-60Hz) under everything for chest-thump weight.
- Large-membrane "taiko/dhol"-style hits (same noise+bandpass technique, tuned lower, longer decay, doubled/tripled hit clusters) on tala downbeats (`Dha`/`Dhin`) for war-drum weight.
- A noise-sweep + rising-filter-cutoff riser (`BiquadFilterNode.frequency` ramped up over ~1-2s) cued 1-2 bars before boss entry/phase transition — standard trailer-riser technique, trivial in Web Audio.
- A driving 8th-note plucked-string ostinato under the melody at high intensity (mechanical, repetitive — contrasts with the more rubato melody at low intensity) for the "epic fusion" propulsion RRR/Baahubali scores use.
- Optional short choir/brass-like stab (`sawtooth` + `triangle` layered through a formant-ish bandpass, fast attack) on the tihai's final hit for maximal impact — reuse the `victory`/`defiance` SFX chord-stack technique already in `audio.js`.

## Common Pitfalls

### Pitfall 1: Oscillator aliasing/harshness
**What goes wrong:** Raw `sawtooth`/`square` oscillators (used for the current drone) sound harsh and aliased at higher pitches — fine for a low drone root, bad for a melodic lead an octave or two up.
**Why it happens:** Naive Web Audio oscillators are band-limited but still generate audible aliasing artifacts as frequency rises, and a raw sawtooth has none of the natural spectral rolloff of a real plucked/blown instrument.
**How to avoid:** Use `triangle`/`sine`-dominant waveforms for the melodic voice, always through a lowpass tracking the fundamental (`filt.frequency = freq * ~3-4`, same ratio the existing drone code already uses), and for pluck-like attack, prefer a short Karplus-Strong delay-loop over a bare oscillator.
**Warning signs:** Melody register sounds "buzzy"/"digital" rather than woody/breathy.

### Pitfall 2: Clicks from unshaped envelopes
**What goes wrong:** Any `gain.value = x` hard-set mid-note, or a `stop()` call without a preceding fade, produces an audible click (discontinuity).
**Why it happens:** Web Audio renders whatever the parameter curve says, including instantaneous jumps.
**How to avoid:** Already solved correctly in this codebase's `tone()`/`noise()` — always `setValueAtTime` then `exponentialRampToValueAtTime` (floor at `0.0001`, never literal `0`, since exponential ramps can't target/leave zero). Reuse this exact pattern for every new voice.
**Warning signs:** Audible "tick"/"pop" on every note-off, especially percussion.

### Pitfall 3: GC churn from per-note node creation
**What goes wrong:** A scheduler firing several bols/beats per second across 3-4 layers creates dozens of short-lived nodes per second; `OscillatorNode`/`AudioBufferSourceNode` cannot be restarted once stopped (single-use by spec), so some node churn is unavoidable — but uncontrolled churn causes GC pauses that can stutter both audio and the render loop sharing the same process.
**How to avoid:** Reuse `AudioBuffer` objects (create once per drum timbre, replay via many disposable `BufferSourceNode`s), route disposable per-note oscillators/sources into a small number of persistent bus `GainNode`/`BiquadFilterNode`s (not a fresh filter per note), null references via `onended` for prompt collection, and hard-cap simultaneous ringing voices per layer (e.g. max 4 percussion voices).
**Warning signs:** Frame-rate dips correlated with dense drum passages (high intensity/boss laggi sections).

### Pitfall 4: Timer drift / not the lookahead pattern
**What goes wrong:** Scheduling notes at the moment a `setTimeout` callback fires (rather than a pre-computed `ctx.currentTime` target) causes audible timing drift, worse under any main-thread load (which this game has — render + physics + hazards all compete).
**How to avoid:** Lookahead scheduler (Pattern 1) — the timer only decides *when to schedule*, never *when to sound*.

### Pitfall 5: Background-tab/window throttling
**What goes wrong:** Chromium (which Electron embeds) throttles `setTimeout`/`setInterval` to as coarse as ~1s when a window/renderer is backgrounded or minimized; a scheduler naively relying on that timer resolution can starve, then dump a burst of stale notes when focus returns.
**How to avoid:** On `visibilitychange`/window blur-focus, re-prime `nextStepTime = ctx.currentTime + smallBuffer` on refocus rather than letting the queued backlog fire all at once. `AudioContext` itself is not throttled the same way (it keeps real time), only the scheduling timer is at risk.

### Pitfall 6: Suspended AudioContext (autoplay policy)
**What goes wrong:** Electron's Chromium still enforces the autoplay-gesture policy in many configurations; a `new AudioContext()` can start `suspended` until a user gesture resumes it.
**How to avoid:** Already handled — `game.js`'s `firstTouch` calls `AUDIO.init(); AUDIO.resume();` on first interaction. Extend this pattern; don't assume the context is `running` at any biome-entry call site — guard `startMusic()`/layer-add calls exactly like existing `sfx()`/`startDrone()` do (`if (!this.ctx || this.muted) return`).
