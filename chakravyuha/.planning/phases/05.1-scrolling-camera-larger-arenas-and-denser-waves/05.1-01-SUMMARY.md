# Phase 05.1 Plan 01: Camera core + arena sizing Summary

**Built the tested pure camera math (scroll clamp, follow/snap, transform, culling, off-screen indicators) that every later 05.1 plan consumes, plus data-driven per-room-kind arena sizes with size-aware layouts and hazards.**

## Performance

- **Duration:** ~20 min active work (two short sessions separated by a rate-limit pause)
- **Completed:** 2026-09-26
- **Tasks:** 2/2 completed
- **Files modified:** 3 (`js/renderer.js`, `js/data.js`, `js/rooms.js`) + `test/smoke.js`

## Accomplishments
- CAMERA now exposes a fully unit-tested world<->screen API (transform, inverse, culling AABB tests,
  off-screen edge/cluster indicators, exponential-damped follow with snap) with zero changes to the
  existing punch/kick/shake/begin/end code paths.
- Arenas are now larger than the 1280x720 viewport and data-driven: combat 2240x1300, boss 1600x960,
  rest 1180x580, all from `DATA.ARENA`, with `ROOMS.worldRect()` exposing the padded world rect for
  Phase 05.4's art placement.
- All 12 room-layout templates gained biome-themed `large` obstacle extras that only materialize in
  large (combat) arenas, validated for bounds/spawn-clearance/door-clearance/reachability at both the
  combat and rest arena sizes.
- Hazard counts (fireVent/venomPool) scale with arena area; tall arenas get a second river band, and
  both bands still exclude the spawn row.
- `ROOMS.enterRoom` sizes the arena before the player is placed and calls `CAMERA.snap()` immediately
  after, so every room transition — including the very first room of a run — starts with a correctly
  clamped, non-swooping camera.

- `js/renderer.js` — added CAMERA scroll/transform state (`sx/sy/tx/ty/tz/VW/VH/CFG`) and pure methods:
  `pad`, `worldRectFor`, `anchor`, `clampScroll`, `lookAhead`, `desiredScroll`, `xform`, `_store`,
  `worldToScreen`, `screenToWorld`, `viewRect`, `visible`, `visibleRect`, `edgePoint`, `clusterIndicators`,
  `_followTarget`, `follow`, `snap`. `begin()`/`end()`/`punch`/`kick`/`update`/`resetFx` unchanged.
- `js/data.js` — added `DATA.ARENA` (origin/sizes/pad/legacyArea/largeArea/maxObstacleScale) and a `large`

- `js/rooms.js` — added `setArena`, `worldRect`, `obstacleScale`, `isLargeArena`, `hazardCountScale`;
  `materializeLayout` now scales circle radii and appends `large` extras in large arenas; `spawnHazards`
  scales fireVent/venomPool counts and adds a second river band for tall arenas; `enterRoom` now derives
  the room kind and calls `setArena` before player placement, then `CAMERA.snap()` right after.
- `test/smoke.js` — new "camera math (Phase 05.1)" suite (10 checks covering every behavior in the plan);
  "room layouts (Phase 4, GAME-03)" validation now runs at both `combat` and `rest` arena sizes; hazard
  placement test recomputes `spawnX/spawnY` from `GAME.arena` after `ROOMS.enterRoom` instead of caching
  a stale pre-room value; new "arena sizing + camera snap on room entry" suite (6 checks: first-room
  combat sizing, sarovar identity transform, boss sizing, in-place mutation, hazard scaling incl.
  2-river-band Vaitarani, post-entry scroll clamping).

## Decisions Made
- Kept `CAMERA.x`/`CAMERA.y` as unused legacy fields (per D-05) rather than repurposing them, so `begin()`
  stays untouched and the ctx-transform/bridge cutover (05.1-02) has a clean diff to work against.
- `_followTarget()` was factored out as a shared private helper for `follow()`/`snap()` (not explicitly
  named in the plan, but keeps the two impure drivers from duplicating the GAME/INPUT/PAD read logic).
- Chose safe fraction ranges ([0.12, 0.88] x, [0.08, 0.92] y, r<=~30px pre-scale) for every template's
  `large` obstacles so spawn/door clearance holds by construction rather than needing per-template
  distance verification.

## Deviations from Plan

None architecturally — plan executed as written. Two minor in-flight test-authoring fixes, both within
Rule 1/3 scope (bugs in the test code I was writing, not in the shipped renderer/rooms/data logic):

**1. [Rule 1 - Bug] Floating-point sector-boundary flakiness in the `clusterIndicators` test**
- **Found during:** Task 1 verification run
- **Issue:** The first `cluster30` sub-test used direction angles (`0`, `±0.66π`) that landed exactly on
  a `clusterIndicators` sector boundary (`(angle+π)/(2π)*16 === 8.0` exactly), so floating-point jitter
  from the ±0.02 rad random offset occasionally split one direction across two sectors, producing 4
  arrows instead of ≤3.
- **Fix:** Moved the three test directions to sector centers (`0.1963`, `2.1599`, `-2.1599`), well clear
  of any bucket boundary.
- **Files modified:** `test/smoke.js` (test-only; no production code change)
- **Committed in:** `b0ee8af`

**2. [Rule 3 - Blocking] Duplicate `ar` identifier in the new Task 2 checks**
- **Found during:** Task 2 verification run
- **Issue:** `const ar = vm.runInContext('__arenaResults', ...)` collided with an existing `const ar` used
  earlier in the file for ambient-particle results, causing a `SyntaxError` at load.
- **Fix:** Renamed the new results binding to `arn` and updated its `check(...)` call sites.
- **Files modified:** `test/smoke.js`
- **Committed in:** `73c7fc1`

**Total deviations:** 2 auto-fixed (both Rule 1/3, test-file-only). **Impact on plan:** none — no
production code or requirement scope changed.
