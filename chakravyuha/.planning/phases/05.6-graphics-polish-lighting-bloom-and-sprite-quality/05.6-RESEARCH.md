# Phase 05.6: Graphics Polish (Lighting, Bloom, Sprite Quality) - Research

**Researched:** 2026-09-26
**Domain:** PixiJS v8 post-processing filters (bloom/glow/color grading), light-map compositing, sprite downscale quality, graphics quality tiers
**Confidence:** HIGH (filter API/versioning — verified against npm/official sources; MEDIUM on integrated-GPU perf, which is hardware-dependent and not independently benchmarked here)

## Summary

The project vendors PixiJS **8.19.0** as a single UMD file (`vendor/pixi.min.js`, no module system, no bundler) — the same constraint applies to whatever filter library is added: it must be a standalone UMD/IIFE bundle loadable via a plain `<script src>` tag, exactly like the existing pixi vendoring pattern. **`pixi-filters` v6.1.5** is the correct package: it is the actively maintained, Pixi-v8-compatible successor to the old per-filter `@pixi/filter-*` packages (those are legacy/v7-era and should not be used), and it ships a browser build at `dist/browser/pixi-filters.min.js` in the npm tarball — vendor that one file next to `vendor/pixi.min.js`. It includes `AdvancedBloomFilter`, `GlowFilter`, `AdjustmentFilter` (brightness/contrast/saturation/gamma — this is the "color grading" tool), `ColorMapFilter` (LUT-based grading), `GodrayFilter`, `OutlineFilter`, and `DropShadowFilter` — all of the filters this phase's questions ask about, in one package.

For lighting: prefer a **light-sprite RenderTexture composited with an additive/multiply blend** over per-object glow filters for anything that needs to "light its surroundings" (fire, astra casts, hazards) — this is cheaper (one extra render pass total, not N filter passes per light-casting object) and composes naturally with the project's existing pooled-particle/`ColorMatrixFilter`-lazy-attach patterns in `js/vfx.js`/`js/sprites.js`. Reserve `GlowFilter`/`AdvancedBloomFilter` for a small, capped number of always-on hero elements (player, active telegraphs) rather than every particle. Normal-map lighting is not worth pursuing — no normal maps exist for any AI-generated sprite, and generating them would require a whole new asset-pipeline stage; skip per the question's own framing.

For sprite quality: generate character key-poses at a higher source resolution (already 1024x1024 for enemies/1024 for bosses' 256 output — the *source* generation is already 1024, only the `finish_sprite.py --size` output is downscaled to 128/256) and increase the **output size**, not the generation size, with LANCZOS (already used in `finish_sprite.py`) plus mild unsharp-mask; enable `resolution`/`autoDensity` scaling (already present in `SPRITES.init`) for 1440p/4K fullscreen; Pixi v8 `Texture` mipmaps help only for *downscaling en-route to a smaller draw size* (useful if 1440p/4K users effectively render sprites larger, not smaller, so mipmaps have limited value here — the bigger win is simply shipping a larger base texture).

**Primary recommendation:** vendor `pixi-filters@6.1.5`'s browser UMD bundle; build lighting via an additive light-map RenderTexture (not per-object glow); apply `AdjustmentFilter` per-biome as one stage filter on `SPRITES.worldContainer`; gate all of it behind a 3-tier Low/Medium/High quality setting that disables filters (not sprites) at Low.

### Alternatives Considered
| Instead of | Could use | Tradeoff |
|---|---|---|
| Per-object `GlowFilter` on every light-casting entity | Additive light-map RenderTexture, multiplied over the scene | Light-map approach is O(1) extra render passes total; per-object filters are O(N) filter passes (one GPU pass per filtered display object) — on an integrated GPU (the dev machine's target-adjacent hardware and likely min-spec Steam Deck/laptop), N filter passes for every fire pit + astra cast will cost far more than one composited light layer |
| `ColorMapFilter` (LUT) | `AdjustmentFilter` (sliders) | LUT gives more filmic/precise grading but requires authoring a LUT texture per biome (new asset, new pipeline step); `AdjustmentFilter` needs no new assets and is tunable in code — start with `AdjustmentFilter`, only invest in LUTs if sliders can't hit the target look |
| Baked sprite outline (dilate in `finish_sprite.py`) | `OutlineFilter` at runtime | Runtime outline costs a filter pass per outlined sprite every frame; a baked outline (one-time post-process step added to `finish_sprite.py`) costs nothing at runtime — prefer baked for the player/enemies since their silhouette doesn't change frame to frame, reserve `OutlineFilter` only for a dynamic case (e.g. a temporary "marked" status effect) if one is ever needed |

## Architecture Patterns

### Recommended structure
```
SPRITES.worldContainer            # existing
├── bgContainer                   # existing (biome bg / floor)
│   └── lightMapSprite            # NEW: PIXI.Sprite(lightMapRenderTexture), blendMode 'add' or 'multiply', composited after bg, before entities OR as a full-container filter (see Pattern 1)
├── entityContainer                # existing
└── fxContainer                    # existing (VFX particles, already additive-capable per js/vfx.js _tryAttach)

worldContainer.filters = [AdjustmentFilter]     # NEW: one per-biome color-grade stage, cheap (single container-level filter)
[specific hero sprites].filters = [AdvancedBloomFilter]   # NEW: capped list, not every sprite
```

### Pattern 1: Additive light-map RenderTexture (recommended primary lighting approach)
**What:** A dedicated `PIXI.RenderTexture` (e.g. sized to the arena, or viewport-sized and following the camera) that light-casting sources (fire pits, astra casts, hazard glows, boon pickups) render simple radial-gradient sprites into every frame (additive blend within the light-map render), then composited once over the main scene with `blendMode: 'add'`.
**When to use:** Any "light source that lights its surroundings" requirement — this is exactly what `Success Criteria #1` (light sources glow and light their surroundings) asks for, and it scales to an arbitrary number of lights without an arbitrary number of filter passes.
**Example:**
```javascript
// Pattern, informed by PixiJS v8 RenderTexture + additive blend docs (pixijs.com/8.x guides).
// Source: PixiJS official docs structure (RenderTexture + Sprite compositing) — verify exact
// v8 RenderTexture.create/resize API against https://pixijs.com/8.x/guides/components/textures
// before implementation; this is the compositing PATTERN, not verbatim tested code.
const lightMapRT = PIXI.RenderTexture.create({ width: A.w, height: A.h });
const lightMapStage = new PIXI.Container();   // lights render into here each frame
// ... per-light: a radial-gradient PIXI.Sprite added to lightMapStage, blendMode 'add' ...
app.renderer.render({ container: lightMapStage, target: lightMapRT, clearColor: 0x000000 });
const lightMapSprite = new PIXI.Sprite(lightMapRT);
lightMapSprite.blendMode = 'add';   // Pixi v8 blend mode is a string, not the old BLEND_MODES enum
SPRITES.bgContainer.addChild(lightMapSprite);
```
**Why this over per-object glow:** the existing `js/vfx.js` particle system already proves this project's perf posture — it hard-caps ambient particles at 15% of `CAP` specifically to protect frame budget, and already uses additive blend mode for embers/sparks (`add: true` param, `blendMode` set to `'add'`/`'normal'` per-particle in `_renderPixi`). A light-map is the same idea one level up: composite once, not per-light.

### Pattern 2: Per-biome color grading via `AdjustmentFilter` on `worldContainer`
**What:** One `AdjustmentFilter` instance per biome (swapped on biome change, mirroring how `SPRITES.setBackground` already swaps textures on biome change), applied to `SPRITES.worldContainer.filters`.
**When to use:** Success Criteria #1's "per-biome color grading" — cheapest correct implementation; a single filter pass over the whole already-composited world layer, not per-sprite.
**Example:**
```javascript
// Source: pixi-filters README (AdjustmentFilter constructor options: gamma, saturation,
// contrast, brightness, red/green/blue, alpha) — verify exact option names against the
// vendored dist file's TS types/README once downloaded.
const grade = new PIXI.filters.AdjustmentFilter({ saturation: 0.9, contrast: 1.08, brightness: 0.97 });
SPRITES.worldContainer.filters = [grade];   // swap `grade`'s params per biome.id on biome change
```

### Pattern 3: Bloom on a capped hero-element list
**What:** `AdvancedBloomFilter` applied only to specific sprites: the player (subtle, ties into the existing `PLAYER_LIFT` brightness treatment already in `_applyFlash`), boss phase-2 sprites (ties into existing ember/divine phase2 tint), and active telegraph/danger-zone graphics.
**Example:**
```javascript
// Compose with the EXISTING lazy-filter-array pattern already used in js/sprites.js _applyFlash
// (spr.filters = [liftF, flashF]) rather than inventing a new filter-management convention.
if (!spr._bloomF) spr._bloomF = new PIXI.filters.AdvancedBloomFilter({ threshold: 0.6, bloomScale: 0.8 });
spr.filters = [...(spr.filters || []), spr._bloomF];
```

### Anti-Patterns to Avoid
- **A `GlowFilter` or `AdvancedBloomFilter` on every particle sprite in `VFX._px.sprites`** (up to 2048 sprites per `CAP`): this would add up to 2048 filter passes per frame — catastrophic on any GPU, let alone integrated. Use the light-map approach for particle-driven glow instead (or simply keep particles additive-blended with a bright base texture, which already reads as "glowing" without a filter, per the existing `emberCv`/`dotCv` gradient textures in `js/vfx.js`).
- **Re-deriving blend-mode constants from Pixi v7 (`PIXI.BLEND_MODES.ADD`)**: Pixi v8 blend modes are lowercase strings (`'add'`, `'multiply'`, `'normal'`) as already used correctly in `js/vfx.js` (`const bm = p.add ? 'add' : 'normal'`) — keep this convention, don't reintroduce the old enum.
- **Filtering `SPRITES.app.stage` (includes `hudContainer`)**: color grading and bloom must apply only to `worldContainer` (the game world), never to `hudContainer` (HUD/UI must stay screen-accurate and unaffected by biome mood grading) — mirrors the existing camera-shake isolation already built between `worldContainer` and `hudContainer`.

## Sprite Quality

### Current pipeline (verified from `tools/art/finish_sprite.py`, `prompts.json`)
- Characters generate at **1024x1024** (`character_size`) already — this is already "high-res source."
- `finish_sprite.py` already uses `Image.LANCZOS` for the fit-to-size resize step — the recommended filter is already in use.
- Output size is currently capped at `--size 128|256` (enemies/bosses respectively) via an `argparse choices=[128, 256]` constraint.

### Recommended changes
1. **Raise the output-size ceiling**, not the generation size (generation is already 1024): add `512` (or keep at 256 but rely on Pixi's own upscale-with-good-filtering at render time) as an allowed `--size` for bosses specifically, since bosses render larger on-screen (`BOSS_HEIGHT_PER_R` already boosts their scale) and are the ones most likely to look soft when downscaled hard from 1024→256 then upscaled back up on-screen by the sprite-layout scale factor. **This is the actual "blurry sprite" risk in this pipeline: a 1024px generation is finished down to a 256px atlas frame, then Pixi scales that 256px frame back UP to the on-screen size (`r * HEIGHT_PER_R`) — that up-then-down-then-up path is where detail is lost, not the initial generation.** Increasing the `finish_sprite.py` output ceiling reduces this loss directly.
2. **Add a mild unsharp-mask/sharpen pass** in `finish_sprite.py` after the LANCZOS resize, using Pillow's `ImageFilter.UnsharpMask` (stdlib-adjacent, Pillow is already a pipeline dependency) — a small radius/percent (e.g. radius=1.5, percent=60, threshold=2) restores perceived crispness lost in the LANCZOS downscale without introducing new artifacts. This is a one-line addition to an existing script, not a new tool.
3. **Baked outline over runtime `OutlineFilter`** for all standard character sprites (see Anti-Pattern above under Don't Hand-Roll below) — add an optional dilate-and-stroke step to `finish_sprite.py` (Pillow `ImageFilter.MaxFilter` on the alpha channel, then composite a dark ring behind the original) so the outline ships baked into the atlas frame, costing zero runtime filter passes across potentially dozens of on-screen enemies.
4. **Mipmaps:** Pixi v8's `Texture`/`BaseTexture` support `autoGenerateMipmaps` — but mipmaps only help when a texture is drawn *smaller* than its native size (mipmap chain picks a lower-res level to avoid shimmer/aliasing). Given this project's actual problem is the reverse (small source frame scaled UP to on-screen size), mipmaps provide little value here; **skip mipmaps, prioritize the larger output-size + sharpen fix above instead.**
5. **Consistent light direction:** the existing `style_positive` prompt template has no explicit light-direction instruction; add one (e.g. "soft light from upper-left, consistent rim light") to `prompts.json style_positive` so newly (re)generated character key-poses agree with whatever the light-map/bloom pass assumes as the "sun" direction — needed for the lit-sprite look to read coherently once dynamic lighting exists. This is a prompt-only change, no new tooling.

### Recommended in-game sizes
| Context | Current | Recommendation |
|---|---|---|
| 1280x720 viewport (base target) | player ~52px tall (r13 * HEIGHT_PER_R 4), enemies similar, bosses larger via `BOSS_HEIGHT_PER_R` | Keep on-screen sizes as-is (gameplay-tuned, per 02-CONTEXT-AMENDMENT's readability findings) — the quality fix is in *texture* resolution feeding that same on-screen size, not the on-screen size itself |
| 1440p/4K fullscreen | `SPRITES.init` already sets `resolution: window.devicePixelRatio || 1, autoDensity: true` (confirmed present in `js/sprites.js` line 52-53) | Already correct — Pixi will render at native device pixel ratio; the *texture* source resolution (item 1 above) is what determines whether that higher-resolution render actually shows more detail or just a bigger blur. No `SPRITES.init` change needed, only the texture pipeline changes above. |

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---|---|---|---|
| Bloom/glow | A custom two-pass blur+threshold shader | `pixi-filters` `AdvancedBloomFilter`/`GlowFilter` | Already GPU-optimized, already Pixi-v8-native, zero new shader code to write/debug/maintain |
| Color grading | Per-pixel manual RGB math in a custom filter | `pixi-filters` `AdjustmentFilter` (or `ColorMatrixFilter`, already used for hit-flash) | `AdjustmentFilter` is purpose-built for exactly brightness/contrast/saturation/gamma; reinventing it risks subtly wrong color math |
| Sprite outlines | A runtime edge-detection shader | Baked dilate-in-post (Pillow, in `finish_sprite.py`) for static character silhouettes; `OutlineFilter` only for genuinely dynamic cases | Baked is strictly cheaper for content that doesn't change shape frame-to-frame (all of this project's characters) |
| Light compositing | A full deferred-lighting/normal-map G-buffer pipeline | Additive light-map RenderTexture (Pattern 1) | Full deferred lighting needs normal maps (no pipeline step generates them, and AI-generated painterly sprites don't have a natural normal-map source) — massively out of scope for a 2D top-down illustrated game; the additive light-map gets 90% of the visual win at a fraction of the engineering cost |

**Key insight:** every filter/lighting need in this phase maps to an existing `pixi-filters` filter or an extension of a pattern (`ColorMatrixFilter` lazy-attach, additive particle blending) already proven in this exact codebase — there is no case here that justifies a custom shader.

## Common Pitfalls

### Pitfall 1: Filtering too many display objects per frame
**What goes wrong:** Applying any `pixi-filters` filter to dozens of individual sprites (all enemies, all particles) tanks frame rate on integrated GPUs, because Pixi must render each filtered object to an intermediate render target before compositing.
**Why it happens:** It's the most "obvious" way to add glow — filter each glowing thing individually.
**How to avoid:** Cap filtered objects to a small, named list (player, boss, telegraphs) and route everything else (particles, ambient effects) through the additive light-map / additive-blend-texture approach instead.
**Warning signs:** FPS drop correlates with enemy/particle count rather than staying flat — check via the existing `VFX.renderDebug` overlay (already shows FPS + particle count) before/after adding filters, same worst-case-load stress test pattern already used in Phase 3 (03-03-SUMMARY.md's "worst-case load" stress run).

### Pitfall 2: Filtering `hudContainer` or the whole `app.stage`
**What goes wrong:** Color grading/bloom bleeds into HUD text/icons, making them dim, oversaturated, or blurry, and breaks the existing camera-shake isolation (`hudContainer` is deliberately outside `worldContainer` per `js/sprites.js` comments).
**How to avoid:** Only ever set `.filters` on `SPRITES.worldContainer` or specific children within it — never on `SPRITES.app.stage` or `SPRITES.hudContainer`.

### Pitfall 3: `pixi-filters` version mismatch with the vendored Pixi core
**What goes wrong:** `pixi-filters` versions before v6 target Pixi v7's filter API; mixing a v7-targeted filters build with the vendored Pixi 8.19.0 will throw at filter-construction time or silently no-op.
**How to avoid:** Confirm `pixi-filters@6.x` specifically (not an older cached tarball) and smoke-test one filter (e.g. `AdjustmentFilter` with default params on a single sprite) immediately after vendoring, before building out the rest of the lighting/grading system.

### Pitfall 4: Baked-outline dilate step clipping thin details
**What goes wrong:** A naive alpha-dilate (grow silhouette by N px, fill with dark color behind original) can visually thicken already-thin features (naga tail tip, weapon silhouette) disproportionately at small sprite sizes.
**How to avoid:** Keep the dilate radius small (1-2px at the *output* resolution, scaled with the new larger output-size recommendation above) and visually spot-check against the existing contact-sheet review pattern (`tools/art/contact_sheet.py`) before batch-applying to all 21 existing atlases.

## Graphics Quality Settings Tiers

Building on the existing `SETTINGS` global (`js/settings.js`, already has `reducedParticles`, `hitstop`, `screenFlash` toggles per Phase 3) — add a single `graphicsQuality: 'low'|'medium'|'high'` setting.

| Tier | Bloom/Glow | Color grading | Light-map | Baked outlines | Particles | Notes |
|---|---|---|---|---|---|---|
| **Low** | Off (no `pixi-filters` instantiated at all) | Off | Off (no light-map RenderTexture allocated) | On (baked, zero runtime cost — always safe to keep) | `reducedParticles` forced on (reuses existing VFX-01 toggle, ~35% count per `VFX.count()`) | Target: integrated GPUs / Steam Deck-class hardware; matches the "graphics quality settings let lower-end machines disable expensive effects" success criterion directly |
| **Medium** | On, capped hero-list only (player + boss) | On (`AdjustmentFilter` per biome) | On, lower resolution (e.g. half-res RenderTexture) | On | Default (no forced reduction) | Recommended default for unknown/mid hardware |
| **High** | On, hero-list + telegraphs/hazards | On + optional `GodrayFilter` in Naraka | On, full-res | On | Default | Dev-machine / high-end target; matches the phase's "frame rate holds at target in worst-case combat on the dev machine" success criterion for validation |

**Implementation note:** gate filter *instantiation*, not just visibility — an instantiated-but-invisible Pixi filter still costs a render pass in some cases; at Low tier, simply never construct the filter objects (`spr.filters = null`, no `AdjustmentFilter`/`AdvancedBloomFilter` ever created), mirroring the existing lazy-construction discipline already used for `_liftF`/`_flashF` in `js/sprites.js`.
