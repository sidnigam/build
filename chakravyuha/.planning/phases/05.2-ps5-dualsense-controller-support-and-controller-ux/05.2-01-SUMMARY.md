# Phase 05.2 Plan 01: DualSense detection, twin-stick aim, rebindable bindings Summary

**PAD now classifies DualSense/DualSense Edge/DualShock4/Xbox/generic pads from their `gamepad.id`, follows whichever of several connected pads the player touches, aims world-space with right-stick-primary/left-stick-fallback/hold-last twin-stick logic plus an optional non-sticky aim-assist-lite, dashes along the left stick (falling back to the rebindable keyboard vector, then aim), drives actions from a STORE-persisted rebindable button map with a capture hook for a future rebind UI, and no longer cancels a keyboard/mouse player's attacks just because a pad happens to be plugged in.**

## Performance

- **Duration:** ~50 min active work
- **Completed:** 2026-09-27
- **Tasks:** 2/2 completed
- **Files modified:** 4 (`js/gamepad.js`, `js/settings.js`, `js/entities.js`, `test/smoke.js`)

## Accomplishments

- `PAD.familyFromId`/`modelFromId` classify DualSense (`054c:0ce6`), DualSense Edge (`054c:0df2`),
  DualShock 4 (`054c:05c4/09cc/0ba0`), Xbox (vendor `045e` or `xbox|xinput|microsoft` substrings) and
  generic pads from both Chromium (`... Vendor: 054c Product: 0ce6)`) and Firefox (`054c-0ce6-...`) id
  formats — vendor id checked before the generic substring fallback so an Xbox pad's own "Wireless
  Controller" substring can never be misread as a DualShock 4.
- `PAD.mapGamepad` now reads the PS (16) and touchpad (17) buttons, `LS`/`RS` stick clicks, and analog
  `LT`/`RT` trigger values (pressed at `value >= 0.3` or `pressed`), all tolerant of gamepads that expose
  fewer than 18 buttons (never throws, missing indices read as not-pressed).
- `PAD.pickPad` keeps the previously active pad connected and idle, but hands control to any other
  connected pad that shows activity (a button press or a stick beyond the 0.5 activity threshold) —
  whichever of several plugged-in PS5 pads the player actually touches drives the game.
- A full rebindable action-binding layer: `PAD.DEFAULT_BINDINGS`, `PAD.bindings` (STORE-persisted under
  `chakravyuha_padbindings_v1`), `applyPadRebind` (pure — steals the button from any other action, and
  always leaves `pause` with a `Start` fallback), `actionDown`, `load/save/resetBindings`, plus
  `captureNext`/`captureStep` (wait-for-release, then next rising-edge button name, 5s timeout) for a
  future rebind UI.
- Twin-stick world-space aim: `PAD.resolveAim` (right stick if deflected, else left stick, else hold the
  last angle) feeds `PAD.aimAssist` (snaps to the best-scored live enemy within ~15°/460px of the raw
  intent angle, gated by `SETTINGS.aimAssist`, re-derived every frame from the unassisted intent so it
  never becomes a sticky lock). `poll()` writes the result into `INPUT.wx/wy` only while
  `INPUT.device === 'pad'`.
- `PAD.chooseDashDir` (left stick > rebindable keyboard move vector > aim) now drives
  `Player.tryDash()`'s direction, replacing the old hardcoded `w/a/s/d`+arrow-key literals — rebound
  movement keys now steer the dash too.
- Fixed the 05-02 bug where `poll()` unconditionally wrote `INPUT.lmb = RT || A` whenever any pad was
  connected, cancelling a keyboard/mouse player's mouse attacks the instant a pad was plugged in (even if
  untouched). All pad-driven writes to `INPUT.lmb`/aim/`ax`/`ay` now happen only while
  `INPUT.device === 'pad'`.
- Added a public `PAD.state` snapshot (connected/index/id/family/model/label/mapping/pads/buttons/
  triggers/axes/left/right/edges/actionEdges/dt/rumble/assistTarget) for the later 05.2 plans (glyphs,
  focus manager, rumble, controller test screen) to read without re-deriving from `navigator.getGamepads()`.
- `SETTINGS.DEFAULTS` gained `aimAssist: true`, `rumble: true`, `rumbleIntensity: 0.8` (the existing
  generic bool/0..1-clamp load/set path handles them with no other settings.js changes).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `familyFromId` misclassified an Xbox pad as PlayStation**
- **Found during:** Task 1, writing the DualSense-vs-Xbox classification smoke tests.
- **Issue:** The initial implementation checked the ps/xbox substring regexes (`dualsense|dualshock|
  playstation|wireless controller` vs `xbox|xinput|microsoft`) before vendor id, and checked ps first.
  `"Xbox Wireless Controller (STANDARD GAMEPAD Vendor: 045e Product: 0b13)"` contains the substring
  "wireless controller", so it was classified `'ps'` instead of `'xbox'`.
- **Fix:** Reordered detection to check vendor id (`054c` -> ps, `045e` -> xbox) first, then the `xbox`
  substring check, then the `ps` substring check last — vendor id is authoritative when present, and the
  more specific "xbox" substring is checked before the generic "wireless controller" one.
- **Files modified:** `js/gamepad.js`.
- **Verification:** `familyFromId('Xbox Wireless Controller (STANDARD GAMEPAD Vendor: 045e Product:
  0b13)') === 'xbox'` now passes; all other family/model smoke checks still pass.
- **Committed in:** `32e43dc` (Task 1 commit — fixed before commit, not a separate follow-up commit).

**2. [Rule 3 - Blocking, test-only] Pre-existing 05.1-02 aim test needed isolating from the new
   aim-assist feature**
- **Found during:** Task 2, tracing the pre-existing "world-space aim (Phase 05.1)" smoke test against
  the new `poll()`.
- **Issue:** That test asserts `INPUT.wx/wy` land at an *exact* `player.pos + AIM_REACH * (cos/sin angle)`
  point after a right-stick poll. `GAME.enemies` at that point in the file carries over whatever earlier
  full-run/boss/death simulations left in it; the new `aimAssist` (on by default) scans `GAME.enemies`
  and could snap the exact angle to a leftover enemy, breaking the exact-equality assertion.
- **Fix:** Saved/restored `GAME.enemies` around that test's pad-aim sub-case, setting it to `[]` so
  aim-assist has nothing to snap to (mirrors the plan's own instruction to do the same in the new
  integration tests).
- **Files modified:** `test/smoke.js` (test-only; no production code changed).
- **Committed in:** `17e948a` (Task 2 commit).
