## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] INTENSITY stem-gain table violated its own stated loudness rule**
- **Found during:** Task 1
- **Issue:** The `<music_spec>`'s literal INTENSITY table gives `sum(L5)/sum(L1) ≈ 2.83`, contradicting the plan's own D-05 rule ("L5's summed stem gain may be at most ~2x L1's") and the Task 1 behavior bullet that tests exactly this ratio (`<= 2.2`).
- **Fix:** Rescaled all 6 rows to compress the dynamic range to a ~1.92x ratio, preserving monotonicity (tabla/big/metal/sub non-decreasing, drone non-increasing) and the L0-percussion-silent rule. `RAGAS` carries an explicit "copy exactly" instruction in the spec; `INTENSITY` does not, so this was in the executor's discretion per the plan's "Claude's Discretion" section.
- **Files modified:** `js/music.js`
- **Commit:** `69272e3`

**2. [Rule 1 - Bug] Anti-repeat mutation could break leap/direction/nyas invariants**
- **Found during:** Task 2
- **Issue:** An early implementation of the "no two consecutive non-mukhda phrases share the same signature" guarantee patched an already-built phrase's first note in place when a collision was detected, using an unfiltered raga-notes pool. This could (and did, in testing) produce a note that violated the within-phrase leap<=7 constraint, the walk-note up/down direction constraint, or (for single-note phrases) the phrase-ending-on-nyas constraint.
- **Fix:** Replaced in-place patching with regenerate-then-fallback: each generator (bank/walk phrase, taan, wail, tar-touch) either draws a fresh candidate from a pre-validated pool, or — for genuinely deterministic paths — applies a pc-preserving octave shift as a last resort (shifting can't change any pc, so it can't break any pc-based invariant, only the degree signature).
- **Files modified:** `js/music.js`
- **Commit:** `989e965`

**3. [Rule 1 - Bug] `forceNyasEnding` tie-break ambiguity on same-note landings**
- **Found during:** Task 2
- **Issue:** When a phrase's forced final note happened to land exactly on the same degree as the previous note (a legitimate "same-note" landing), the direction-classification convention used internally (`curDeg >= prevDeg` counts as "up") could disagree with the same convention used by the smoke test, occasionally producing a note whose pc was valid only in `down` while being classified as `up` (or vice versa).
- **Fix:** `forceNyasEnding` now only accepts a same-degree ("tied") candidate if its pc is valid in *both* `up` and `down`, making it safe under either tie-break interpretation.
- **Files modified:** `js/music.js`
- **Commit:** `989e965`

### Test-only fixes (no production code change)

- The initial `stream.tail(3)` smoke check tried to independently reconstruct "the last completed phrase" from an external `absStep` scan, which is structurally incompatible with `createLeadStream`'s always-1-cycle-ahead lookahead scheduler (by design, per D-09). Rewritten to validate the API contract instead (bounded length, valid raga degrees, changes as the stream advances).
- The initial "mukhda lands on sam" / "phrase ends on nyas" checks could flag a phrase that was merely truncated by the test's own collection window (a mukhda's final note can land a full cycle past wherever its own phrase was planned). Fixed by scanning 2 extra lookahead cycles and excluding the trailing (possibly-incomplete) phrase from structural per-phrase analysis.
- The initial "pluckAt L3 ostinato in order" check assumed the ostinato index stays globally sequential across tala-cycle boundaries; since the index is keyed off the matra (which resets every cycle), this only holds within each cycle for talas whose matra count isn't a multiple of 4 (Rupak=7, Jhaptaal=10). Fixed by checking order per-cycle.
