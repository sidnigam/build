## 05.1 Contract (assumed — verify first)

- `INPUT.mx/my` = **screen-space** mouse position (HUD crosshair drawn in the screen-space HUD pass).
- `INPUT.wx/wy` = **world-space** aim point; `Player.update()` computes `this.aim` from it (`Math.atan2(I.wy - this.y, I.wx - this.x)`).
- The camera scrolls; the world pass (between `CAMERA.begin()` and `CAMERA.end()` in `GAME.render()`) draws in world coordinates.
- **If 05.1 used different names** (e.g. kept `mx/my` as world coords, or added a `CAMERA.screenToWorld`), the executor adapts: PAD writes to *whatever field `Player.update`'s `this.aim =` line consumes*. Confirm with `grep -n "this.aim =" js/entities.js` and `grep -n "wx\|wy" js/game.js js/entities.js js/renderer.js`.
- **If 05.1 derives `wx/wy` from `mx/my` + camera every frame** (for the mouse), that derivation must be skipped while `INPUT.device === 'pad'` or it will overwrite the stick aim. The one-line guard is permitted at that exact site (game.js or entities.js) — this is the only allowed entities.js edit besides `tryDash()`.

## Decisions (locked)

- **D-01 Detection (PAD-01).** Chromium exposes DualSense (054c:0ce6), DualSense Edge (054c:0df2) and DualShock 4 (054c:05c4/09cc/0ba0) with `mapping === 'standard'` over USB and Bluetooth on macOS and Windows (verified against Chromium `gamepad_standard_mappings_mac.mm` / `_win.cc`: `MapperDualSense` maps buttons 0–15 standard, **16 = PS/Home (META)**, **17 = touchpad click**, 18 buttons total; the **mute button is not exposed**). Typical ids: `"DualSense Wireless Controller (STANDARD GAMEPAD Vendor: 054c Product: 0ce6)"` (Chromium), `"054c-0ce6-DualSense Wireless Controller"` (Firefox), `"Wireless Controller (STANDARD GAMEPAD Vendor: 054c Product: 09cc)"` (DS4). `PAD.familyFromId(id)`: vendor `054c` or id containing `dualsense|dualshock|playstation|wireless controller` → `'ps'`; vendor `045e` or `xbox|xinput|microsoft` → `'xbox'`; else `'generic'` (generic uses Xbox-style labels). Missing button indices read as not-pressed. Non-standard mapping is still read with standard indices but flagged in the test screen.
- **D-02 Multi-pad (PAD-01).** `PAD.pickPad(gps, prevIndex)`: keep the previous pad while connected; switch to any other connected pad that shows activity this frame (button pressed or stick beyond 0.5); first pick prefers `mapping === 'standard'`. The user has several PS5 pads — whichever they touch takes over.
- **D-03 Default PS mapping (kept from 05-02, now data-driven + rebindable).** Standard-name bindings `PAD.DEFAULT_BINDINGS = { attack:['RT','A'], special:['LT','X'], dash:['B','RB'], cast:['Y'], pause:['Start','Touchpad'] }` → on PS: attack R2 / ✕, special L2 / □, dash ○ / R1, astra (cast) △, pause Options / touchpad click. L1 stays unbound (05-02 design had no L1 action — documented free slot). PS button (16) is never bound: on macOS it opens the system Game/Launchpad overlay by default. Menu confirm/back are fixed ✕ (A) / ○ (B) and not rebindable (platform convention).
- **D-04 Trigger threshold.** L2/R2 count as pressed at `value >= 0.3` or `pressed` (DualSense triggers are analog; Chromium reports value + pressed).
- **D-05 Aim (PAD-02).** `PAD.resolveAim(left, right, prevAngle)` → right stick if deflected, else left stick (twin-stick convention), else hold. The unassisted "intent" angle is stored separately from the assisted output so aim-assist never becomes a sticky lock. `PAD.aimAssist(px, py, angle, enemies, cfg)`: among live enemies (`!dead`, `!(spawnT > 0)`) within `RANGE = 460` px and within `CONE = 0.26` rad (~15°) of the intent angle, pick the lowest `|angleDiff| + dist/2000` and snap to it; else unchanged. `SETTINGS.aimAssist` (default `true`) only affects the pad.
- **D-06 Dash (PAD-03).** `PAD.chooseDashDir(ax, ay, kbVec, aim)`: analog left stick if non-zero, else keyboard vector from `PAD.digitalMoveVector(INPUT.keys, INPUT.bindings)` (fixes the hardcoded WASD literals in `tryDash`, so rebound movement keys also steer the dash), else aim.
- **D-07 Mouse/pad coexistence bug fix.** 05-02's `poll()` writes `INPUT.lmb = RT || A` every frame whenever any pad is connected, which cancels mouse attacks for a KBM player with a pad plugged in. Pad-driven writes to `INPUT.lmb` / aim fields happen only while `INPUT.device === 'pad'`.
- **D-08 Glyphs (PAD-04).** New `js/glyphs.js` global `GLYPHS`. PS: ✕ ○ □ △ L1 R1 L2 R2 L3 R3 Create Options PS Touchpad; Xbox/generic: A B X Y LB RB LT RT LS RS View Menu; KBM: key names from `INPUT.bindings` (Space, Esc, ↑, E…) plus LMB/RMB/Mouse. PS face buttons are badges in their classic colors: cross blue `#7ea6ff`, circle red `#ff6b6b`, square pink `#ff8fd0`, triangle green `#3fd6a0`. DOM hints use `<span class="glyph …">`; canvas HUD draws the face shapes as vector paths (no reliance on font coverage for ✕○□△). Live switching: `GLYPHS.refresh()` runs at the top of every `PAD.poll()`, compares a signature (device + family + bindings) and re-renders all `[data-glyph-hint]` elements and toggles `body.pad-mode` only on change.
- **D-09 Menu hints.** Per-panel hint footers (`div.pad-hint[data-glyph-hint=KEY]`) are injected by `UI.ensurePadHints()` (ui.js, additive) instead of editing each panel's markup; they are visible only in `body.pad-mode`. The hub controls line (already visible for KBM) becomes device-aware and is built from the live bindings (so keyboard rebinding shows up too). The only edit to existing hub markup is wrapping that text in `<span id="hub-controls-text" data-glyph-hint="hub">` (the erase-save button is left intact).
- **D-10 Focus manager (PAD-05).** New `js/focus.js` global `FOCUS`. Virtual focus only (CSS class `.pad-focus`, **no native `el.focus()`** — avoids Space/Enter activating buttons behind the keyboard dash binding). Active panel = last visible `.panel` in DOM order (settings stacks above hub/pause; the controller-test panel is placed last). Focusables: `button, .card, input[type=range], input[type=checkbox], select` that are visible; `#btn-wipe` is excluded (it uses native `confirm()` which a pad cannot operate). Spatial nav: pure `FOCUS.pickNext(rects, cur, dir)` (half-plane candidates, score = primary distance + 2 × orthogonal offset, no wrap). D-pad or left stick (threshold 0.5, dominant axis) with repeat (first move immediate, repeat after 0.35 s every 0.12 s). ✕ = confirm (click; checkbox toggles + dispatches `change`; select cycles to next option + `change`; range does nothing). ←/→ on a range input steps value ±5 and dispatches `input` + `change`; on a select cycles. ○ = back via `FOCUS.PANEL_BACK` map (settings → BACK, controller test → BACK, shop → LEAVE, shrine/armory/codex → RETURN, pause → RESUME; boon pick / death / victory / hub have no back). Options on pause → resume; Options on settings → back. **Pass-through panel:** the controller test screen (`ctest`) is listed in `FOCUS.PASSTHROUGH` — FOCUS consumes pad input there (so nothing leaks to combat/pause) but performs no navigation/confirm/back, because the user must be able to press ✕/○ to *test* them; exit is **hold ○ for 1 s** (or Options held 1 s, or clicking BACK), rumble test is **hold △ for 1 s** (or clicking TEST RUMBLE). **Armed guard:** when the active panel changes, confirm/back are ignored until all face buttons are released (a held ✕ from combat can never auto-pick a boon). Re-rendered panels (shop purchase, shrine buy, armory select) keep the focused index. Right stick Y scrolls `#codex-list` and the settings panel. Focused element is kept in view via `scrollIntoView({block:'nearest'})`. Focus ring: gold outline + soft gold glow (+ `translateY(-4px)` on cards), only under `body.pad-mode`.
- **D-11 Aim indicator (PAD-06).** When `INPUT.device === 'pad'`, `renderHUD` skips the crosshair; a new `GAME.renderAimIndicator(ctx)` draws, in the **world pass**, a gold arc (±0.35 rad) at `P.r + 30` plus a chevron at `P.r + 44` pointing along `P.aim`, and a small gold diamond on the aim-assist target if one is locked. Geometry comes from a pure `GAME.aimIndicatorGeom(px, py, aim, r)`.
- **D-12 Rumble (PAD-07).** Presets (base magnitudes, scaled by `SETTINGS.rumbleIntensity`, default 0.8): `kill` 40 ms weak .25/strong 0; `hit` 60 ms .35/.10; `crit` 80 ms .5/.2; `hurt` 160 ms .5/.6; `heavy` 320 ms .8/1.0; `test` 500 ms .6/.9. Priority: a weaker preset never interrupts a stronger one still playing; same-tier repeats throttled to ≥ 50 ms. Sources: `VFX.emit` is wrapped once (idempotent) from gamepad.js — `hit`→hit, `crit`→crit, `death`→kill, `hurt`→hurt, `phase`/`bossDeath`→heavy — plus a per-poll detector: `GAME.shake` jumping by ≥ 10 while a boss is alive → heavy (boss slam), and `GAME.state` becoming `'dead'` → heavy. No edits to vfx.js/entities.js damage code. Plays only when `INPUT.device === 'pad'` and `SETTINGS.rumble` is on; `playEffect('dual-rumble', …)` promise rejections swallowed. **Known limitation:** Chromium implements rumble for DualShock 4 over HID and via CoreHaptics on macOS; DualSense rumble support depends on OS/Chromium version. The test screen reports `supported` / `unsupported` and the rumble test result. DualSense lightbar/adaptive triggers are **not** reachable via the Gamepad API — skipped.
- **D-13 Pad rebinding (PAD-08).** `PAD.applyPadRebind(bindings, action, btn)` (pure): action gets `[btn]`; `btn` is removed from every other action; `Home` cannot be bound; `pause` always retains `Start` as a fallback. Persisted under STORE key `chakravyuha_padbindings_v1`; `PAD.resetBindings()`. Capture via `PAD.captureNext(cb)`: waits until all buttons are released, then delivers the next rising-edge button name and suppresses all other pad handling that frame. There is no cancel button (○ must itself be capturable); an unused capture times out after 5 s.
- **D-14 Settings additions.** SETTINGS keys: `aimAssist: true`, `rumble: true`, `rumbleIntensity: 0.8` (existing generic bool/0..1 clamp handles them). Settings panel gains a Controller section: rumble toggle, rumble intensity slider, aim-assist toggle, pad rebind rows showing glyphs, "Reset controller bindings", "Controller test" button. Panel becomes vertically scrollable (overflow-y auto) since it now exceeds 720 px.
- **D-15 Controller test screen (PAD-09).** New `#ctest` panel (last in DOM). Shows: status line (family, model, id, mapping, index, connected pad count), two stick boxes with live dots (deadzone ring drawn), L2/R2 bars with numeric values, an 18-button glyph grid lit when pressed, rumble support + "Test rumble" button (plays `test` preset), and a help block visible when no pad is detected. Hold-to-act (○ 1 s = back, Options 1 s = back, △ 1 s = rumble test) with a visible progress fill, via pure `UI.ctestHold(hold, buttons, dt)`. Updated by a `requestAnimationFrame` loop that runs only while the panel is visible; the view-model is a pure `UI.ctestModel(PAD.state)` (headless-tested).
- **D-16 Electron (PAD-10).** `electron/main.js`: `backgroundThrottling: false` and `autoplayPolicy: 'no-user-gesture-required'` in `webPreferences`, `show: false` + `ready-to-show` → `show()` + `focus()`. The Gamepad API needs no flags in Electron; the window must be focused (Chromium only delivers gamepad data to the focused, visible page). In the browser, the first pad button press also calls `AUDIO.init(); AUDIO.resume()` (best effort — browsers may not treat a pad press as a user gesture; the hub hint notes that a click/key may be needed once for sound).

## Connection help (also shown in-game on the controller test screen)

1. **USB:** connect with a data-capable USB-C cable, then press the **PS** button.
2. **Bluetooth pairing:** with the controller off, hold **Create + PS** for ~3–5 s until the light bar flashes rapidly.
   - macOS: System Settings → Bluetooth → "DualSense Wireless Controller" → Connect.
   - Windows: Settings → Bluetooth & devices → Add device → Bluetooth → "Wireless Controller".
3. Focus the game window and **press any button** — browsers only expose a controller after a button press.
4. If Steam is running with PlayStation Configuration Support, Steam Input may present the pad as an Xbox controller (Xbox glyphs appear) — expected; quit Steam or disable it for the browser test.
5. macOS: the PS button opens the system game overlay/Launchpad by default (System Settings → Game Controllers). The game never uses the PS button.
6. Rumble may be unavailable for DualSense depending on OS/browser version — the test screen says so.

## File ownership (this phase)

`js/gamepad.js`, `js/glyphs.js` (new), `js/focus.js` (new), `js/ui.js` (additive functions + one-line hooks), `index.html`
(script tags, `#ctest` markup, settings Controller container, hub hint span, `<style id="controller-css">` block — the
existing `<style>` and `#settings-css` blocks are not edited), `js/game.js` (renderHUD crosshair/labels, new
`renderAimIndicator`/`aimIndicatorGeom`, one call in `render()`; plus the 05.1 aim-derivation guard if needed),
`js/entities.js` (`tryDash` direction lines only, plus the conditional 05.1 guard), `js/settings.js` (three DEFAULTS keys),
`electron/main.js` (window options), `test/smoke.js` (files list + appended sections). **Not touched:** `js/audio.js`,
`js/sprites.js`, `js/vfx.js`, `assets/**`.

Because every plan appends to `test/smoke.js` (and several share `js/gamepad.js` / `index.html`), plans run in
sequential waves 1 → 4 (same rationale as Phase 5's wave note).

## Deferred / out of scope

- DualSense lightbar, adaptive triggers, haptics beyond dual-rumble, gyro, touchpad as pointer (not in the Gamepad API).
- Keyboard-only menu navigation (arrow keys/Enter) — mouse + pad cover it; revisit for Steam Deck verification (Phase 7).
- Steam Input API integration / Steam glyph API (Phase 6/7).
- Per-weapon or per-action aim-assist tuning UI beyond the on/off toggle.
