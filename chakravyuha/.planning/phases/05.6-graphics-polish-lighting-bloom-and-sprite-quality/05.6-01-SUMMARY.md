## Verified Pixi API Names (vendor/pixi.min.js, read directly before use)

- `app.renderer.resize(width, height, resolution)` — resolution is a genuine third optional argument (`resize(t,e,i){i||(i=this._resolution),...}`); no fallback branch was needed.
- `app.canvas` getter exists (`get canvas(){return this.view.canvas}`); used directly, `app.view` kept only as the plan's documented fallback (never hit).
- `app.renderer.resolution` getter/setter exists on the renderer.
- `app.renderer.gl` is the raw WebGL context (`this._renderer.gl=t` in the context-change handler) — `gl.getExtension('WEBGL_debug_renderer_info')` works as a standard WebGL call.
- `Filter` constructor takes a `resolution` option and exposes it as a plain settable instance property (`this.resolution=t.resolution`); `clipToViewport` defaults to `true` (`Pe.defaultOptions={...,clipToViewport:!0}`).
- `Spritesheet#textureSource` is the underlying `TextureSource`; `autoGenerateMipmaps`, `mipmapFilter`, `maxAnisotropy` are plain settable properties directly on it (not nested under `.style`), and `updateMipmaps()` recomputes `mipLevelCount` from `autoGenerateMipmaps` (verified: 50x524 player atlas -> `mipLevelCount: 10` = `floor(log2(524))+1`).
- `AdjustmentFilter({gamma,contrast,saturation,brightness,red,green,blue,alpha})` and `AdvancedBloomFilter({threshold,bloomScale,brightness,blur,quality,kernels,pixelSize})` constructor option names taken from the tarball's `lib/*/*.d.ts` — exactly as CONTEXT's research_corrections said, confirmed independently.
- **TextureSource.resizeCanvas()** (the autoDensity bugfix root cause): `this.autoDensity&&"style"in this.resource&&(this.resource.style.width=\`${this.width}px\`,...)` — runs on every `resize()` call, pinning CSS size to the fixed logical width/height.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `autoDensity: true` silently made GFX-07's entire premise unreachable**

- **Found during:** Task 3, browser verification of the 1080p resolution run — `RES` kept reporting `1, css=1280` no matter what `--size` was passed.
- **Root cause:** `SPRITES.init()` (pre-existing, Phase 2 code, not written by this plan) passed `autoDensity: true` to `PIXI.Application.init()`. Pixi's `TextureSource.resizeCanvas()` — called internally on every `renderer.resize()`, including both the app's own init-time resize AND every call this plan's `GFX.applyResolution()`/`SPRITES.setResolution()` makes — unconditionally sets `canvas.style.width = "<logicalWidth>px"` and `canvas.style.height = "<logicalHeight>px"` (verified by reading `vendor/pixi.min.js` directly: `resizeCanvas(){this.autoDensity&&"style"in this.resource&&(this.resource.style.width=\`${this.width}px\`,this.resource.style.height=\`${this.height}px\`)}`, with `this.width`/`this.height` fixed at the Application's configured `1280`/`720`, never derived from the container). Since that inline style always wins the CSS cascade over the pre-existing `canvas#game{width:100%;height:100%}` stylesheet rule, the canvas's `getBoundingClientRect().width` could **never** be anything but exactly `1280` CSS px, regardless of actual viewport/fullscreen size — making `GFX.applyResolution()`'s `cssW = canvas.getBoundingClientRect().width` always equal `1280`, so `displayResolution()` always computed `1`, and the render resolution could never actually "follow the display" as GFX-07 requires. Independently confirmed this was *not* the intended design: `js/game.js`'s pre-existing `mousemove` handler already does `(e.clientX - r.left) * (this.W / r.width)` — scaling that is meaningless unless the canvas's CSS width is expected to vary from the logical 1280.
- **Fix:** `autoDensity: false` in `SPRITES.init()`'s `app.init()` options (one-line change, within this plan's `js/sprites.js` file ownership). Pixi's `resolution` option continues to control backing-store pixel density completely independently of this flag; disabling it simply stops Pixi from fighting the pre-existing, already-correct `#game{width:100%;height:100%}` CSS rule. Verified empirically with a standalone CDP debug script (not committed — scratchpad-only) before and after the fix: before, `canvas.getBoundingClientRect()` stayed `{width:1280,height:720}` at a 1920x1080 emulated viewport with an inline `style="width:1280px;height:720px"`; after, it correctly reports `{width:1920,height:1080}` with no inline style, letting CSS govern.
- **Files modified:** `js/sprites.js`.
- **Verification:** the 1080p browser-check run now reports `RES 1.5 css=1920` exactly as D-08 specifies (`displayResolution(1, 1920, 2) = 1.5`). `node test/smoke.js` stays green (headless has no `navigator`/`document.createElement('canvas')`-backed Pixi app, so this code path never runs in the smoke sandbox). No other behavior changed — mouse-aim math, HUD bridge, and camera transforms were already written assuming a responsive canvas CSS size.
- **Committed in:** `2e7049e` (Task 3 commit).

**Total deviations:** 1 auto-fixed bug (Rule 1). No architectural deviations (Rule 4) were needed — the fix is a single boolean flag flip, fully within this plan's `js/sprites.js` file ownership, required to make the plan's own explicit GFX-07 success criterion achievable at all.

## Issues Encountered

**Headless Chrome + SwiftShader + pixi-filters is impractically slow for Medium/High verification.** `AdvancedBloomFilter`'s internal extract+multi-pass-blur filter chain, run through SwiftShader's pure-CPU WebGL rasterizer, made a single `btn-begin` → settle cycle take many minutes (observed GPU-process CPU pinned at 300-500% for 5-7+ minutes without completing) — consistent with CONTEXT's own "SwiftShader FPS is indicative only" framing, just more severe than expected. Resolved by using `tools/browser-check.mjs`'s own `--gpu` flag (real Apple M1 Pro ANGLE Metal rendering) for all Medium/High/1080p/regression runs, which completed in seconds at a real 60 FPS. Low tier (zero filters) was verified directly on SwiftShader, which stayed fast throughout. This is a property of the dev machine's headless-Chrome/SwiftShader interaction with multi-pass filters, not a code defect — no code changes resulted from this finding beyond already having the `--gpu` flag available (built as part of this same task, per D-24).

Separately, headless Chrome's CDP WebSocket connection was intermittently flaky across this session (a `send()` call would occasionally never receive its response, hanging the whole script) — unrelated to GFX; retrying the same `browser-check.mjs` invocation always succeeded on the next attempt, and independent fresh-connection debug probes confirmed the page itself was never actually unresponsive or crashed. No code changes made for this (pre-existing `tools/browser-check.mjs` CDP plumbing from Phase 05.1, out of this plan's scope to rewrite); documented here for the next executor's awareness in case it recurs.
