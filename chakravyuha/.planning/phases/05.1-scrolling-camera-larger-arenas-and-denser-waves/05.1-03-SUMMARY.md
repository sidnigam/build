# Phase 05.1 Plan 03: Denser waves Summary

**Data-driven wave composition (DATA.WAVES + per-biome `waves` blocks) drives Naraka room 1 to ~21 mostly-weak enemies across 3 overlapping waves (up from a legacy 2-4), ramping to ~30-55 units with real elite pressure by each biome's last room, all under a 26-alive cap with a drip-fed spawn queue, arena-wide pack spawns, and engage-range-gated ranged AI.**

## Accomplishments

- **DATA.WAVES** (maxAlive 26, weak fodder multipliers, timing/spawn-distance/pack tunables,
  engageRange 640, eliteCost 3) plus a `waves` block on every `DATA.BIOMES` entry (count/perWave/
  fodder/fodderShare/eliteShare, lerped by room index) — one place to retune density.
- **Pure wave composition**: `ROOMS.waveParams`/`composeWave`/`planRoom` turn a budget into unit
  lists (`{id, weak}`), proven by a statistical smoke suite (N=200 plans per biome/room, N=50
  composeWave calls per biome with random budgets/shares): Naraka room 1 averages 21.0 units
  (86% weak, exactly 3 waves); every biome's threat and (for Ranabhoomi) elite count ramp from
  first to last combat room; legacy numeric `spawnWave(16)` path stays non-empty, biome-valid,
  and weak-unit-free.
- **Alive cap + drip queue**: `ROOMS.spawnUnits` never lets `GAME.enemies` exceed 26 alive,
  queuing overflow on `GAME.spawnQueue`; `ROOMS.drainQueue` drips it back in (batches of 3 every
  0.35s) as room opens up. Spawns land in packs (3-6 units) placed via `pickPackCenter`/
  `placeUnit`: 360-950px from the player, obstacle-clear, never within 220px, spread across the
  *whole* arena (`findClearSpawnPoint` no longer restricted to the right 70%).
- **Overlapping waves**: the next wave now triggers once the previous is ~70% cleared
  (`alive <= ceil(lastWaveSize * 0.3)`) instead of waiting for zero survivors; the room only
  clears once alive, `GAME.waves`, and `GAME.spawnQueue` are all empty.
- **Large-arena fairness**: archer/naga only fire within `engageRange` (640px) and approach when
  far instead of sniping off-screen; naga now approaches when far (previously stood still at any
  range); yatudhana approaches when far and never summons past the alive cap. Coins vacuum to the
  player from anywhere once a room clears (900px/s pull), while the in-combat 90px magnet is
  unchanged.
- **Root-caused and fixed** the pre-existing flaky `riverCurrent` hazard smoke test (deferred from
  05.1-02) — a test-fixture bug, not game logic (details in Deviations).

## Deviations from Plan

**1. [Orchestrator-directed, not a deviation] Root-caused and fixed the deferred flaky riverCurrent test**
- **Found during:** stability sweep after Task 3 (running the suite ~20x turned up ~3/20 failures).
- **Issue:** `riverCurrent: pushes the player along its direction` intermittently failed with
  "player displacement too small". Root cause: the test fixture hardcodes the player at the
  arena's horizontal center to test the river hazard's push in isolation, but vaitarani's
  `vait_fords` layout template (1 of 3, picked at random by `ROOMS.buildArena`) runs a near-full-
  height column of `pit` obstacles through that exact x. When that template landed and the river
  band's y overlapped a pit segment, `clampToArena`'s obstacle-push-out pinned the player against
  the pit edge every frame, masking the river's own push.
- **Fix:** `test/smoke.js` — clear `GAME.pillars = []` before positioning the player in this
  fixture only, isolating the push-math check from the room's obstacle layout (matching how the
  surrounding per-hazard fixtures already isolate their own concern). Test-only change; no
  production code touched.
- **Verification:** 15 consecutive clean runs, then a further 10/10 clean run per the
  orchestrator's explicit ask.
- **Files modified:** `test/smoke.js`, `deferred-items.md`.
- **Committed in:** `2e32664`

**2. [Rule 1 - Bug, test-only] Fire-detection race in the archer/naga engage-range fairness tests**
- **Found during:** Task 3, while writing the fairness smoke checks (initial version was flaky
  ~1/6 runs).
- **Issue:** Checking `GAME.eprojectiles.length > 0` only *after* the simulated window ended could
  read `0` even when the enemy had fired, because a projectile that hit the player (or expired)
  before the window closed is filtered out of the array the same frame — a timing race in the
  test, not in the fire-gating logic itself (which was already correct).
  Confirmed by re-running the original assertion 20x (kept failing intermittently) vs. the fixed
  version (10/10 clean, then a further 20/20 clean in the final stability sweep).
- **Fix:** Track "ever fired" by checking `GAME.eprojectiles.length > 0` *inside* the simulation
  loop (OR-accumulated across frames) instead of only at the end. Test-only change.
- **Files modified:** `test/smoke.js`.
- **Committed in:** `303aac2`

**Total deviations:** 1 orchestrator-directed root-cause fix (explicitly requested, not scope
creep) + 1 auto-fixed test-only timing bug (Rule 1). No production-code deviations from the
plan's specified actions.
