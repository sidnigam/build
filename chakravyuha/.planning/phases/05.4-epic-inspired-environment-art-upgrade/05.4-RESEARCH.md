# Phase 05.4: Epic-Inspired Environment Art Upgrade - Research

**Researched:** 2026-09-26
**Domain:** SDXL/ComfyUI environment art generation for a larger scrolling-camera arena (~2240x1300, boss ~1600x960), Mahabharata/Ramayana set-dressing
**Confidence:** MEDIUM-HIGH (pipeline mechanics HIGH — verified against this repo's own tools; checkpoint licenses MEDIUM — verified via web, not hands-on; Flux feasibility MEDIUM)

## Summary

The Phase 2 pipeline (`tools/art/*`) already produces exactly the kind of "even, no-focal-point, seamless-tiling" ground textures that this phase needs — 02-08's biome backgrounds were explicitly tuned toward that look after rejecting compositions with a focal point. The core move for 05.4 is **not a new checkpoint or a new tool**, but reframing the existing biome-background approach as a *tileable base texture* (draw with `PIXI.TilingSprite`, confirmed available in vendored Pixi v8) plus a new layer of **individually-generated, rembg-cutout prop sprites** (chariot wheels, banners, chains, naga pillars) placed as one-off set dressing on top — this is what turns "generic tile" into "detailed epic backdrop" without paying for expensive upscaling of a single huge image.

For the checkpoint: stay on the **SDXL 1.0 base architecture family** (not Flux) so the existing `comfy_client.py` graph, `sd_xl_base_1.0.safetensors` checkpoint field, and prompt/negative structure keep working unmodified — only the checkpoint filename changes. Recommend **DreamShaper XL** (CreativeML OpenRAIL++-M, same license family already recorded in `PROVENANCE.json.checkpoint_license`, and known for painterly/illustrative output rather than Juggernaut's photoreal lean) as the upgrade target for backgrounds/props needing more painterly detail than the plain `sd_xl_base_1.0` checkpoint delivered. Flux.1-schnell is Apache-2.0 (commercially clean) but is 3-5x slower on Apple Silicon and needs a GGUF-quantized workflow on 16GB unified memory — not worth the pipeline rewrite for this phase; keep it as a documented fallback only.

**Primary recommendation:** Keep the SDXL txt2img pipeline; swap in DreamShaper XL for backgrounds/props; tile a smaller seamless ground texture across the larger arena via `TilingSprite` instead of generating/upscaling one huge image; layer epic-specific cutout props on top; never place walkable deity imagery.

## Architecture Patterns

### Recommended composition (Hades-style layered arena)
```
worldContainer
├── bgContainer
│   ├── TilingSprite (seamless ground texture, biome-specific)   # NEW: replaces single-image bgSprite for arenas larger than 1 source image
│   ├── prop sprites (rembg-cutout, biome set-dressing)          # NEW: sparse, non-tiling, hand-placed
│   └── existing bridge-canvas floor tint/vignette/darken (game.js renderBackground) — keep, still readability-critical
├── entityContainer  (unchanged — sprites, weapons, markers)
└── fxContainer      (unchanged)
```

### Pattern 1: Seamless tile + TilingSprite (replaces single stretched bg for larger arenas)
**What:** Generate one biome ground texture at native SDXL resolution (1024-1344px) with the existing "even distributed detail, no focal point, seamless repeating texture" prompt language (already proven in `prompts.json` for ranabhoomi/patala/vaitarani), verify it tiles without an obvious seam, then draw it via `PIXI.TilingSprite` sized to the actual arena bounds (2240x1300, boss 1600x960) instead of `finish_biome.py`'s current cover-crop-to-1280x720.
**When to use:** All 4 biome floors, now that arenas exceed one source image's coverage.
**Example:**
```javascript
// Source: pixijs.com/8.x/guides/components/scene-objects/tiling-sprite (v8 API)
const floor = new PIXI.TilingSprite({
  texture: SPRITES.textures['bg:' + biome.id],
  width: arena.w,
  height: arena.h,
});
floor.tileScale.set(arenaTileScale);  // tune so texture pixel density matches sprite scale
SPRITES.bgContainer.addChildAt(floor, 0);
```
**Seam check:** self-review step (mirrors existing D-14a agent review) must include "tile the accepted PNG 2x2 and inspect for a visible seam" before accepting a background for tiling use — SDXL does NOT guarantee edge-wrap continuity even with "seamless" in the prompt; treat visible seams as a rejection criterion the same way 02-08 treated "focal point" compositions as rejections.

### Pattern 2: Prop sprites via existing finish_sprite.py path (not finish_biome.py)
**What:** Generate individual epic-relevant props (broken chariot wheel, dhvaja banner, chain segment, naga wall carving) as isolated txt2img subjects on the existing plain-grey-background style template, run through `finish_sprite.py` (already does rembg + despeckle + trim), NOT `finish_biome.py`. Place as ordinary `PIXI.Sprite` instances at hand-authored or room-template-driven positions in `bgContainer`, above the tiling floor and below entities.
**When to use:** Focal detail that a repeating texture cannot provide — this is the direct fix for "generic tiling floor" feedback from 02-08/02-11 lessons and the user's "needs more detailed designs" note.
**Avoid hand-rolling:** reuse `finish_sprite.py` unmodified (it already supports arbitrary `--size`; add a size like 192 or 256 for a mid-sized prop) rather than writing a new post-processing script.

### Pattern 3: Prompt patterns for top-down 3/4 consistency (extends `biome_positive_template`)
Existing template: `"top-down orthographic view looking straight down at {ground}, painted game arena floor texture, even evenly distributed detail, low contrast, no focal point, ..."` — keep this exact framing for the *tileable base layer*. For **props**, use a different, focal template (props ARE meant to have a focal point, unlike the floor):
```
"{prop}, top-down 3/4 isometric-adjacent game prop, painted illustration, cast shadow baked in, Hades-adjacent painterly style, {palette}, plain flat pale grey background, no characters, no text"
```
This mirrors the character `style_positive` template (plain background for clean rembg cutout) rather than the biome template (no plain-background instruction, since biome art doesn't get cutout).

### Anti-Patterns to Avoid
- **Generating one enormous 2240x1300 image directly:** SDXL's native training resolution is ~1024px; forcing a single huge generation produces compounding artifacts (duplicated limbs/objects, incoherent large-scale structure) well documented as a SDXL failure mode at 2x+ native res. Tile instead, or use Ultimate SD Upscale in tiled img2img mode if a single unique large image is truly required.
- **Baking cracks/detail at one fixed orientation with no variation:** a single tiled texture repeating exactly is more visible at 2240px than it was at 1280px (more repeats fit on screen); consider generating 2 variant tiles per biome and randomly assigning per room, or accept some visible repetition and rely on props to break it up (cheaper, matches "prop set-dressing" requirement anyway).
- **Placing deity imagery as a floor decal.** See cultural constraint below — this is a hard rule, not a style preference.

### Cultural constraint — IMPORTANT (hard rule, not discretionary)
**No deity imagery may be placed as a floor decal that the player walks/stands on.** This extends CLAUDE.md's "gods are allies only" rule: stepping on sacred imagery (a god's face, a yantra/mandala representing a deity, an idol) is broadly considered disrespectful in Hindu practice. The existing chakravyuha mandala floor pattern in `game.js renderBackground` (lines 642-655) is an abstract geometric labyrinth motif, not a deity depiction, and is already fine. When generating naga wall-carvings or banner emblems: **carvings/banners go on walls/props (vertical or prop-plane), never as a texture the player's feet visually overlap on the ground plane.** Route this through the same self-review checklist used for character generation (D-14a) with an explicit added checklist item: "no face, idol, yantra, or recognizable deity symbol in the ground-texture layer."

## Common Pitfalls

### Pitfall 1: SDXL base gives generic/tiling-looking floor textures (already observed, 02-08)
**What goes wrong:** SDXL, when asked for a ground texture, defaults to a repetitive, low-information "texture" read rather than an illustrated scene — exactly the "generic tiling floor" feedback the user gave.
**Why it happens:** The `biome_positive_template` explicitly asks for "no focal point, even distributed detail" (needed so the texture doesn't fight gameplay readability) — but that same instruction is what makes it look generic without props layered on top.
**How to avoid:** Treat the floor texture as *intentionally* plain/tileable (that's correct, not a bug) and put all the "epic detail" into the separate prop-sprite layer instead of fighting the floor prompt toward busier compositions (which 02-08 already tried and rejected as "focal point" failures for ranabhoomi).
**Warning signs:** If a new floor-texture prompt keeps producing rejected "focal point" compositions (radial/circular arrangements, single dominant object) the way ranabhoomi did across 3 attempts, that's a signal the detail belongs in props, not the floor prompt.

### Pitfall 2: Ranabhoomi-style prompt drift toward circular/radial composition
**What goes wrong:** Requesting "scattered battlefield debris" without a texture-specific anchor phrase causes SDXL to compose debris into a mandala/shield-like radial arrangement (documented in 02-08-SUMMARY.md, 3 rejected seeds).
**Why it happens:** SDXL's training data over-represents circular/radial "hero shot" compositions for battlefield/debris scenes.
**How to avoid:** Use the exact phrase pattern that already worked — "seamless repeating texture, evenly scattered small debris" — for any new floor-texture prompt, and avoid "wheel", "arrangement", or other implicitly-radial nouns in the floor prompt (reserve "wheel" for the standalone chariot-wheel *prop* prompt, which is allowed to have a clear silhouette).

### Pitfall 3: Generating at 2x SDXL native resolution directly
**What goes wrong:** A single txt2img call at ~2240x1300 (vs. SDXL's native ~1024) produces duplicated objects, broken large-scale coherence, and much longer generation time on the M1 Pro.
**How to avoid:** Generate at native res (1024-1344, matching the already-used `biome_size`) and tile via `PIXI.TilingSprite`, per Pattern 1 above. Reserve Ultimate SD Upscale (tiled img2img) only for a genuinely unique, non-repeating large image (e.g. a one-off boss-arena backdrop) if that's ever wanted — not for the standard 4-biome floor.

### Pitfall 4: Prop sprites break scale consistency with existing character sprites
**What goes wrong:** Props generated at `character_size` (1024x1024) but scaled ad hoc in-engine can end up mismatched with the r-based `SPRITES.CFG.HEIGHT_PER_R` scaling already used for characters, looking either toy-sized or gigantic next to the player.
**How to avoid:** Author prop prompts with an explicit real-world-relative scale cue in the prompt text (e.g. "a chariot wheel roughly waist-height on a human figure") and manually tune each prop's in-engine scale against the player's known on-screen height (~52px, r13 * HEIGHT_PER_R 4) during self-review, the same way sprite `HEIGHT_PER_R_OVERRIDE` is already used per-actor.

## Open Questions

1. **Does DreamShaper XL actually look better for this project's specific "Hades-adjacent painterly, Indian mythology" style than the plain SDXL base?**
   - What we know: DreamShaper XL is broadly reputed for painterly/illustrative output vs. SDXL base's more generic output (the exact complaint in user feedback).
   - What's unclear: No side-by-side test has been run with this project's exact locked style/negative prompt template.
   - Recommendation: Before committing, run 1-2 test generations (a biome floor + one character) with the new checkpoint through the *existing unmodified* `prompts.json` templates, self-review against the existing checklist, and only adopt if visibly better — otherwise stay on the already-license-verified `sd_xl_base_1.0`.

2. **How many prop types are enough per biome to satisfy "detailed designs" without overloading generation time?**
   - What we know: 02-08/02-11 averaged ~4.3 min/image with a 1-5 retry rate per subject.
   - What's unclear: exact prop count the planner should budget (this is a planning decision, not a research one).
   - Recommendation: Budget 4-6 unique prop sprites per biome (reusing 1-2 across rooms via random placement) as a starting point — matches the existing per-biome asset density (1 floor + a handful of hazards/obstacles already exist in `js/rooms.js`/`js/game.js`).
