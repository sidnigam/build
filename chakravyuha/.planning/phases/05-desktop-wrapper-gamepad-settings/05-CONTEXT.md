# Phase 5 Context — Desktop Wrapper + Gamepad + Settings

Source: orchestrator delegation (discuss-mode auto — recommended defaults chosen, locked here).

## Decisions (locked)

- **D-01 (Electron shell):** Electron 42 main process at `electron/main.js` + `electron/preload.js`. `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. Window 1280x720 min, resizable, F11 fullscreen toggle. Preload exposes `window.chakraNative = { isDesktop:true, saveRead(name), saveWrite(name,json), setFullscreen(bool), getFullscreen(), quit() }` via `contextBridge`. `saveRead`/`getFullscreen` use `ipcRenderer.sendSync` (synchronous — the renderer's existing save/load code is synchronous today, this avoids an async rewrite of `meta.js`/`settings.js`). `saveWrite`/`setFullscreen`/`quit` use fire-and-forget `ipcRenderer.send`. Main process writes JSON atomically (tmp file + rename) under `app.getPath('userData')/saves/<name>.json`.
- **D-02 (Packaging):** electron-builder 26 config lives in `package.json` `"build"` key. `appId: com.chakravyuha.game`, `productName: Chakravyuha`. mac target dmg (arm64+x64, `identity: null` — unsigned for now, signing/notarization is Phase 7's job). win target nsis x64 (built in CI later — Phase 7 note, not validated locally this phase since we're on macOS). `files` includes `index.html, js/**, assets/**, vendor/**, electron/**` and excludes `**/_raw/**`, `**/_review/**`, `**/reference/**`. `"main": "electron/main.js"`. Scripts: `start:desktop`, `dist:mac`, `dist:win`. `electron` + `electron-builder` installed as devDependencies.
- **D-03 (Storage abstraction):** New `js/storage.js` defines global `STORE` with `get(name, fallback)` / `set(name, value)` / `remove(name)`. Three modes, resolved by a pure `STORE.resolveMode(hasChakraNative, hasLocalStorage)` function: `desktop` (chakraNative present) → `browser` (localStorage present) → `headless` (in-memory `Map`-like object). Desktop mode lazily migrates: first `get()` for a key with no chakraNative-side value falls back to reading the same key from `localStorage` (still available in the Electron renderer) and writes it through to chakraNative once (PLAT-04). `js/meta.js` is edited surgically: `localStorage.getItem/setItem/removeItem` calls become `STORE.get/set/remove`.
- **D-04 (Input abstraction):** New `js/gamepad.js` defines global `PAD`. Pure, headless-testable functions: `PAD.applyDeadzone(x,y,dz)` (radial deadzone with rescale, default `dz=0.2`), `PAD.mapGamepad(gp)` (reads a W3C-standard-mapping-shaped object into `{lx,ly,rx,ry,buttons:{A,B,X,Y,LB,RB,LT,RT,Back,Start,...}}`), `PAD.digitalMoveVector(keys, bindings)` (keyboard → normalized `{dx,dy}` using `INPUT.bindings`). `PAD.poll()` is guarded with `typeof navigator === 'undefined'` (headless-safe, matches the existing `SPRITES` pattern) and is called once per frame from `GAME.frame()`. Left stick (after deadzone) → `INPUT.ax/ay` (analog move axes). Right stick (after deadzone) → when its magnitude exceeds the deadzone, sets `INPUT.mx/my = player.x/y + dir*140` so `entities.js`'s existing `Math.atan2(I.my-y, I.mx-x)` aim code keeps working unmodified. Buttons: RT or A = attack (`INPUT.lmb`), LT or X = special, B or RB = dash, Y = cast, Start = pause — dash/special/cast/pause are edge-triggered (fire once per press, tracked in `PAD._prevButtons`) to match keydown semantics, not held semantics. `INPUT.device` is set to `'pad'` or `'kbm'` on last-used input (added for future glyph work — no consumer this phase; see Deferred).
- **D-05 (Bindings default map):** `INPUT.bindings` (a plain data map, added as a property on the existing `INPUT` object literal in `js/game.js` — this is an allowed edit per file ownership since it's part of "the INPUT object") holds `{ moveUp:['w','arrowup'], moveDown:['s','arrowdown'], moveLeft:['a','arrowleft'], moveRight:['d','arrowright'], dash:[' '], cast:['q'], special:['e'], pause:['escape'] }`. `js/entities.js`'s player movement-read site is rewritten to consult `INPUT.bindings` via `PAD.digitalMoveVector` instead of hardcoded literals, so keyboard rebinding (PLAT-05) actually changes behavior. Gamepad button mapping is fixed to the W3C standard layout this phase (not user-remappable) — Steam Input can already remap upstream; remapping controller buttons in-app is out of scope for this milestone (Claude's discretion, avoids scope creep).
- **D-06 (Settings menu, PLAT-05):** `js/settings.js`'s first task checks whether Phase 3 already created it. If it exists (has `screenShake`/`screenFlash` from VFX-02/04), extend in place with `masterVolume`, `musicVolume`, `sfxVolume`, `resolutionMode` fields and switch its persistence to `STORE` if it isn't already. If it does not exist yet, create it fresh with the full shape. Settings panel DOM added to `index.html` (new `#settings` `.panel`, reachable via a new button in `#hub .menu-btns` and `#pause .menu-btns`). Settings-specific CSS goes in a **separate** `<style id="settings-css">` block — the existing `<style>` block's `.card` rules belong to Phase 2/3 and must not be touched. `js/audio.js` gets a `sfxGain` node inserted between `tone()`/`noise()` output and `master` (currently they connect straight to `master`) plus `setVolume(kind, value)` / `getVolume(kind)` hooks for `master`/`music`/`sfx`. `js/ui.js` gets the settings panel render/wire logic: volume sliders, fullscreen toggle (`chakraNative.setFullscreen`/`getFullscreen` on desktop, Fullscreen API on browser), resolution/scale mode (desktop: window-size presets via a future main-process resize — this phase just persists the choice and applies CSS scale on browser; window-resize wiring is a nice-to-have, not blocking), keyboard rebinding (click a binding row, capture next keydown, write into `INPUT.bindings`), and screen-shake/flash checkboxes bound to `SETTINGS`.

## Deferred / discretion notes (not failures — explicit scope calls)

- **Crosshair swap when using a gamepad** ("hide crosshair, draw aim indicator instead") is **not implemented** this phase. `js/game.js`'s file ownership for this phase is restricted to *only* the `INPUT` object, `bindInput()`, and the per-frame `PAD.poll()` call — `renderHUD()` (where the crosshair is drawn) is out of bounds. Functionally this doesn't block PLAT-02/03: `PAD.poll()` still drives `INPUT.mx/my` from the right stick, so the existing crosshair correctly tracks the virtual aim point on gamepad — it just isn't visually swapped for a different indicator. Revisit in a later phase (e.g. Phase 7 Deck-verification pass) if reviewers flag it.
- **Gamepad-analog dash direction while moving** is a known minor gap: `Player.tryDash()` (a separate method from the movement-read site in `update()`) reads only digital keyboard direction for its dash-direction snapshot; per the strict "ONLY the player movement-read site" file-ownership rule, `tryDash()` is left untouched this phase. When no directional key is held, `tryDash()` already falls back to `this.aim`, which gamepad's right stick correctly drives via `PAD.poll()` — so gamepad dashing still works, it just always uses the aim direction rather than the left-stick direction when moving-and-dashing simultaneously. Acceptable; not a blocker.
- **Gamepad button rebinding** is out of scope — only keyboard actions are rebindable this phase (see D-05).
- **Desktop window-size resize on resolution-preset change** is a nice-to-have; this phase persists the chosen `resolutionMode` via `SETTINGS`/`STORE` and applies it as a browser CSS scale, but does not wire an IPC call to resize the actual Electron `BrowserWindow`. Add later if needed.
- **Windows `.exe` build** is not produced/validated locally this phase (dev machine is macOS) — `dist:win` script is wired but Phase 7's CI (per-OS runner matrix) is where it actually gets exercised, per ROADMAP.

## Wave / dependency note

The delegated instructions suggested plans 05-01 and 05-02 "can execute now" (both unblocked by Phase 3). However both need a `<script>` tag added to `index.html` (storage.js and gamepad.js respectively) and both append assertions to `test/smoke.js` — per GSD's file-ownership-for-parallel-execution rule, two plans touching the same file must be sequential, not same-wave parallel (risk of conflicting/overwritten edits). So: **05-01 = wave 1, 05-02 = wave 2 (depends_on 05-01), 05-03 = wave 3** (depends on both, plus external Phase 3 `js/settings.js`). This is a from-parallel-to-sequential deviation from the loose "can execute now" phrasing, made for correctness; both plans remain fully autonomous with no checkpoints.
