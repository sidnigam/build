# Phase 05.1 Plan 02: Transform/bridge/input integration Summary

**Pixi's worldContainer and the bridge canvas now share one stored transform (tx/ty/tz) computed every frame by CAMERA.begin(), proven pixel-identical by a headless algebraic alignment test; mouse and gamepad aim are world-space (INPUT.wx/wy); and the 05.4 environment-art contract (per-room-kind arena padding, exposed as GAME.arenaPad) is wired into both ROOMS.worldRect() and the camera's own scroll clamp.**

## Performance

- **Duration:** ~45 min active work
- **Completed:** 2026-09-27
- **Tasks:** 2/2 completed
- **Files modified:** 8 (`js/renderer.js`, `js/sprites.js`, `js/game.js`, `js/entities.js`,
  `js/gamepad.js`, `js/data.js`, `js/rooms.js`) + `test/smoke.js`, plus a new
  `deferred-items.md` note

## Accomplishments

- `CAMERA.begin()` is now unconditional and headless-safe: it always computes and stores
  `tx/ty/tz` (via the existing pure `xform()`), then — only when a real Pixi app exists — sets
  `worldContainer.position/scale` and counter-transforms `bridgeSprite` so the bridge canvas
  (drawn in world space via the new `CAMERA.applyCtx(ctx)`) maps to the exact same screen pixels
  as Pixi children. Proven with a 10-point headless test across identity, scroll, and
  scroll+zoom-punch+kick+shake.
- `SPRITES.coverFit`/`setBackground(key, rect)` cover-fit the illustrated biome background against
  the *current room's* world rect (via `GAME._bgRect()` → `ROOMS.worldRect()`) instead of a fixed
  1340x780 rect; the outer dim/fill in `renderBackground` now uses `CAMERA.viewRect(40)` (world
  coordinates) instead of screen-size literals — verified by grep gate (no `this.W`/`this.H`/`1280`/
  `720` literals remain in the world-space render passes).
- `INPUT.wx/wy` is the single world-space aim target: `GAME.syncAim()` (mouse, via
  `CAMERA.screenToWorld`) and `PAD.poll()` (gamepad right stick, now remembering the last angle so
  releasing the stick holds the aim direction) both write it; `Player.update` and the HUD crosshair
  both consume it, with the crosshair projecting the pad's world target back to screen space for
  drawing.
- **Cross-phase 05.4 amendment**: `DATA.ARENA.pad` became `DATA.ARENA.padBySize` — combat/boss
  rooms get `{l:120,r:120,t:200,b:110}` (camera can scroll far enough to reveal architectural walls
  outside the arena edge) while rest rooms keep the exact legacy `{l:50,r:50,t:84,b:56}` (identity
  transform unchanged, confirmed by test). `ROOMS.setArena` exposes the active pad as `GAME.arenaPad`;
  `ROOMS.worldRect()` and `CAMERA.pad()` (feeding both the scroll clamp and the follow anchor) both
  read it, so 05.4 can trust `ROOMS.worldRect()` matches what the camera can actually reveal.

**2. [Rule 1 - Bug, test-only] `GAME.shake` leaking non-zero between test sections caused
   flaky-looking alignment/aim assertions**
- **Found during:** writing the new "camera bridge alignment" and "world-space aim" tests.
- **Issue:** Earlier test sections leave `GAME.shake` non-zero (e.g. from death-path simulations);
  since `CAMERA.begin()` applies random shake jitter whenever `GAME.shake * shakeScale() > 0.5`,
  the identity/scroll-only sub-cases of my own new tests intermittently failed an exact-zero
  assertion purely due to unrelated global state.
- **Fix:** Explicitly reset `GAME.shake = 0` (and restore the saved value in `finally`) before the
  identity/scroll/syncAim sub-cases in both new test sections. No production code changed.
- **Files modified:** `test/smoke.js` (test-only).
- **Committed in:** `836c9a8` / `526626f`

**Total deviations:** 1 amendment (expected, orchestrator-directed) + 1 auto-fixed test-only bug
(Rule 1). No production-code deviations from the plan's specified actions.
