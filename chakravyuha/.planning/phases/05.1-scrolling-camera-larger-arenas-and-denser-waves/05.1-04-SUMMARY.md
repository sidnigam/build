# Phase 05.1 Plan 04: Culling, indicators, browser verification Summary

**Off-screen content (obstacles, hazards, doors, pickups, enemy sprites, particles) is skipped in every world-space render pass via `CAMERA.visible`/`visibleRect`, off-screen alive enemies and cleared-room doors are signposted by clustered HUD edge arrows, and a newly committed headless-Chrome tool (`tools/browser-check.mjs`) proves sub-pixel Pixi/bridge alignment, correct mouse and gamepad world-space aim, and working indicators on a real moved-camera run.**

## Accomplishments

- **Culling (CAM-05):** every world-space render pass now skips off-screen content before drawing —
  `renderBackground` (danger zones, zones, doors, pickups), `renderObstacles` (pillars/walls/pits),
  `renderHazards` (fireVent/venomPool by radius, arrowVolley per marker, riverCurrent by rect),
  `renderEntities` (alive enemies via `CAMERA.visible(e.x, e.y, e.r*3, 96)` before the sprite/fallback
  branch — player is never culled), and `renderEffects` (orbits, player/enemy projectiles, lightning
  bolts, expanding rings, damage texts). `SPRITES.cullEntity(e)` hides a culled entity's
  sprite/marker/weapon (`.visible = false`) while marking it seen so `endEntities()`'s mark-and-sweep
  never destroys/recreates it; `drawEntity`/`drawWeapon` re-set `.visible = true` the moment the
  entity is drawn again. `VFX.inView(p, view)` is a pure AABB helper reused by both the ctx fallback
  and the Pixi particle renderer to hide off-screen particles without releasing them from the pool.
  `GAME.ambientRect()` intersects the arena with `CAMERA.viewRect(120)` so biome ambient particles
  spawn only near the visible part of a 2240x1300 combat arena (falls back to the full arena — never
  empty — when the view doesn't overlap it).
- **Off-screen indicators (CAM-06):** `GAME.indicatorItems()` collects every alive enemy
  (boss-flagged) plus, once a room is `cleared`, its doors; `GAME.renderIndicators(ctx)` draws
  `CAMERA.clusterIndicators()`'s output on the HUD bridge as pulsing triangles (boss arrows larger),
  an inward count badge for clustered arrows, and door arrows with a colored ring + reward glyph —
  wired into `renderHUD` just before the crosshair, whenever not in the hub.
- **Browser verification (CAM-03/CAM-04/CAM-06, WAVE-05):** `tools/browser-check.mjs` (committed,
  usage in its header comment) boots a real run in headless Chrome via CDP, moves the player across a
  combat arena, and numerically proves: `SPRITES.worldContainer.toGlobal` and
  `SPRITES.bridgeSprite.toGlobal` agree exactly for a teleported enemy (dx=dy=0px); mouse world-space
  aim matches `CAMERA.screenToWorld`-derived expected angle (diff ~0.0068rad, well under the 0.01rad
  bar); a mocked gamepad right-stick produces the exact expected world-space aim delta (+140, 0px);
  and off-screen alive enemies produce at least one `CAMERA.clusterIndicators()` arrow. No uncaught
  console errors. Screenshots (in the scratchpad, not committed) confirm the world scrolls between
  spawn and the moved position while the HUD stays fixed and the background covers the whole frame,
  the danger-zone ring lands centered on the teleported enemy's sprite, and edge arrows are visible
  and clear of the HP panel/title/boss bar.

## Deviations from Plan

**1. [Rule 3 - Blocking issue] Runtime.evaluate top-level `const`/`let` collide across separate CDP calls**
- **Found during:** Task 3, first `tools/browser-check.mjs` run — the alignment probe reported
  `{"ok":false,"hasEnemy":false}` and the pad probe reported a stale kbm-device delta instead of the
  expected `(+140, 0)`.
- **Root cause:** Chrome DevTools Protocol's `Runtime.evaluate` runs each call's top-level script in
  the page's shared global lexical environment (REPL semantics) — `const P = GAME.player;` declared
  in one probe's expression collides with `const P = ...` in a later probe (`SyntaxError: Identifier
  'P' has already been declared`), and the script's own `evalJs` helper only reads
  `result.result.value`, silently swallowing the exception instead of surfacing it.
- **Fix:** wrapped every multi-statement probe expression in `(function() { ... })()` so declared
  locals never leak into the global lexical environment; re-ran a minimal repro to confirm the
  `SyntaxError` was the actual cause before applying the fix everywhere.
- **Files modified:** `tools/browser-check.mjs`.
- **Committed in:** `b8e4fb3` (folded into the Task 3 commit — discovered and fixed before first commit).

**2. [Rule 3 - Blocking issue] Pad probe's 100ms wait was too short for headless-Chrome's variable frame rate**
- **Found during:** Task 3, after fixing the scoping bug — the pad probe still intermittently read
  `device: 'kbm'` because `PAD.poll()` runs once per real animation frame and headless SwiftShader
  frame times varied widely (observed FPS from 3 to 60 across runs under this plan's render-cost
  load).
- **Fix:** increased the post-mock wait from 100ms to 400ms (comfortably covers at least one frame
  even at the slowest observed rate); confirmed manually via a direct `PAD.poll()` call that the
  mock + polling mechanism itself was already correct, isolating the issue to timing.
- **Files modified:** `tools/browser-check.mjs`.
- **Committed in:** `b8e4fb3`.

**Total deviations:** 2 auto-fixed blocking issues (Rule 3), both in the new browser tool itself
(discovered and resolved before the first commit of that file — no broken version was ever
committed). No production-code (`js/*.js`) deviations from the plan's specified actions.
