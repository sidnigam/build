- **Pure light model (Task 1):** `GFX.LIGHT_PRESETS` (D-14, every source's starting values), `GFX.collectLights(G, view, tier, envLights, nowSec)` — a pure function covering fireVent/venomPool hazards, the player's ground glow, player/enemy projectiles, orbits/rings/bolts/zones, pickups (coins at High only — `GAME.pickups`' only real item type today is `'mudra'`), doors (once cleared), boss phase-2 auras, ENV prop lights and the registry/transient pools — culled to the view rect, sorted by priority (pulses > boss > hazards > projectiles-nearest-first > pickups/doors > props > coins), capped per tier. `GFX.addLight`/`removeLight` (a `scope:'room'`-aware registry) and `GFX.pulse`/`tickTransients` (a capped-at-32 transient pool) round out the pure half. `SPRITES.addLight`/`removeLight` are thin delegates.

## ENV Takeover Path

**Path used:** `GFX.envPropLights()` reads `ENV._entityItems` (the `{item, obj}` pairs `ENV.build()` populates for every `kind:'prop'`/`'pillar-skin'`/`'wall-skin'` item), filters for `item.frameLight` (set in `ENV._placeProps` from the manifest's `frame.light`), and returns `{x, y, r, color, a, flickerKind}` — skipping anything `ENV` has already culled (`obj.visible === false`), applying `PROP_LIGHT_GAIN` (1.6x) inside the arena and capping margin props at `a ≤ 0.6`.

**Finding (recorded per the plan's own fallback instructions):** as of 05.4-04, `ENV` does **not** build a separate pool sprite for per-prop manifest lights — only biome-ambient `lights.pools` get a `kind:'pool'` sprite in `ENV.lightLayer`. `item.frameLight` is carried on the prop's own entity item with no companion light sprite to hide. So the "hide ENV's matching per-prop pool sprite" half of D-15 has nothing to do today — `GFX` simply adds the light, and there is no double-lighting to resolve. `_restoreEnvPropLights()` stays fully wired (reading `GFX._envHidden`, which this plan's code never populates) so the contract is honored automatically the instant a future `ENV` revision adds a per-prop pool sprite.

`envTakeover` counts of 3–7 across the stress runs confirm the adapter is live against the real, merged 05.4-02 Naraka/Patala env kits (`brazier`/`fire_pit`/`iron_cauldron` for Naraka, `glow_fungus`/`pool_basin` for Patala — all carry `frame.light` in their manifests).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Test-harness `js/gfx.js` load order hit a real V8/vm.runInContext quirk, producing false test failures**
- **Found during:** Task 2, first full smoke run after wiring `VFX.count()`'s `GFX.tier === 'low'` check and the `GFX.pulse()` hooks in `VFX.PRESETS.*`.
- **Issue:** `test/smoke.js` loaded `js/gfx.js` lazily, inside the "GFX core (05.6-01)" test block near the end of the file — by which point thousands of prior `VFX.count()`/`VFX.PRESETS.*` calls (from the file's many full-run simulations) had already executed with `GFX` undefined. Reproduced and confirmed in isolation: a hot function whose `typeof GFX !== 'undefined'` check was compiled/executed many times while `GFX` genuinely didn't exist does not reliably observe a same-named `const GFX` added later by a *separate* `vm.runInContext` script evaluation in the same context — even though the binding is shared and works correctly for functions defined *after* `GFX` already existed. This is a property of Node's `vm` module's global-lexical-environment handling across repeated script evaluations, not a bug in `js/gfx.js` or `js/vfx.js` — production `index.html` always loads `vfx.js` immediately followed by `gfx.js`, before any gameplay code ever calls `VFX.count()` or a `VFX.PRESETS.*` preset, so `GFX` always exists by first call in the real game.
- **Fix:** Added `'gfx.js'` to `test/smoke.js`'s base `files` array, immediately after `'vfx.js'` — the same relative position `index.html` uses. The existing lazy-load guard in the "GFX core" test block (`if (typeof GFX === 'undefined') { ... }`) stays as a harmless no-op fallback.
- **Files modified:** `test/smoke.js`.
- **Verification:** All `VFX`↔`GFX` hook tests (`VFX.count()` low-tier reduction, `VFX.emit('hit')` adding a transient) pass reliably; `node test/smoke.js` is green with 0 failures across repeated runs.
- **Committed in:** `6995d27` (Task 2 commit).

**2. [Rule 1 - Bug] `fireVent`'s real hazard-FSM phase is `'erupt'`, not the illustrative `'active'` the plan/CONTEXT text used**
- **Found during:** Task 1, grepping `js/game.js`'s `updateHazards` per the plan's own explicit instruction ("grep the real item shapes before writing adapters").
- **Issue:** `GAME.hazards`' `fireVent` entries cycle through `'dormant'` → `'warn'` → `'erupt'` → back to `'dormant'`; the string `'active'` never appears anywhere in the real FSM. Implementing `collectLights()` against a literal `phase === 'active'` check (matching the plan's prose/test-fixture wording verbatim) would have made fire vents never actually brighten during real eruptions — a correctness bug disguised as a passing test, since the fixture's own `phase:'active'` would never occur in the real game.
- **Fix:** `collectLights()` keys off `h.phase === 'erupt'` for the bright tier, with an explicit code comment and every smoke fixture matching the real field. `LIGHT_PRESETS.fireVent`'s keys stay named `dormant`/`warn`/`active` (for readability against D-14's own vocabulary) but the selection logic reads the real phase value.
- **Files modified:** `js/gfx.js`, `test/smoke.js`.
- **Verification:** Stress-test fireVents (forced to real `phase = 'erupt'`) visibly brighten in every tier's `stress.png`.
- **Committed in:** `a647cf1` (Task 1 commit).

**3. [Rule 1 - Bug] The `LIGHTALIGN`/telegraph browser-check probes initially picked an arbitrary (often off-screen) `fireVent`**
- **Found during:** Task 3, first Low-tier `--stress` run — `LIGHTALIGN {"ok":false}` and `telegraph.png` showed no visible red ring.
- **Issue:** `(GAME.hazards || []).find(h => h.type === 'fireVent')` returns whichever hazard happens to be first in the array, with no regard for whether it is actually on-screen. In a 2240x1300 arena with up to 8 vents, most are off-screen and correctly culled by `collectLights()`'s view-rect test — not a `GFX` bug, but something the probe must not mistake for a misalignment, and a `dangerZone` telegraph pushed next to an off-screen vent is never visible in the screenshot either.
- **Fix:** Both probes now pick a vent the same way `collectLights()` would keep it — via `CAMERA.viewRect(0)` containment — and the telegraph screenshot reuses the exact same vent the alignment probe found, instead of an independent (and independently arbitrary) search.
- **Files modified:** `tools/browser-check.mjs`.
- **Verification:** All three tiers now report `LIGHTALIGN {"ok":true, ..., dx:0, dy:~0}`, and every `telegraph.png` shows a clearly visible red ring next to an active, on-screen vent.
- **Committed in:** `967d8d1` (Task 3 commit).

**4. [Rule 3 - Blocking] The in-page `--stress` loop could hang the whole verification script indefinitely**
- **Found during:** Task 3, a Low-tier re-run after fix #3 — the script never completed; Chrome's GPU-process helper was found pegged at ~490% CPU for 24+ minutes while the Node process itself used near-zero CPU, i.e. Node was blocked forever awaiting a CDP `Runtime.evaluate` response for a Promise that could never resolve (most likely an uncaught exception inside the in-page `requestAnimationFrame` callback silently halting the rAF chain before `resolve()` was ever reached, per `requestAnimationFrame`'s standard error-handling semantics).
- **Fix:** Added `evalJsTimeout()` (races `evalJs` against a Node-side `setTimeout`, used only for the stress Promise) with graceful `STRESS FAILED` reporting on timeout; wrapped the in-page `tick()` body in its own `try`/`catch` that logs to `console.error` (surfacing as a report-visible console error, matching D-24's own "no uncaught console errors" pass criterion) instead of silently stopping the rAF chain; added a hard `MAX_FRAMES` (1800) circuit breaker as a second line of defense.
- **Files modified:** `tools/browser-check.mjs`.
- **Verification:** Re-ran the full three-tier + regression sequence end-to-end multiple times after this fix with no further hangs; all runs completed in well under a minute each.
- **Committed in:** `967d8d1` (Task 3 commit).

**5. [Rule 1 - Bug] Wash-out: simultaneous-eruption bloom and melee-swarm pulse density**
- Covered in full under "Final Tuned Preset Values" and "Screenshot Observations" above — a readability bug caught by the plan's own required stress-screenshot review step, fixed within the plan's explicit tuning-loop allowance.
- **Committed in:** `967d8d1` (Task 3 commit).
