# Phase 05.1: Scrolling camera, larger arenas and denser waves - Context

**Gathered:** 2026-09-26 (orchestrator-locked; user delegated decisions)
**Status:** Ready for execution

<domain>
## Phase Boundary

Rooms become larger than the 1280x720 viewport with a smooth follow camera. All world-space systems
(Pixi sprites, bridge-canvas primitives, telegraphs, hazards, obstacles, doors, particles, input) work
under a moving camera. Combat pacing shifts to more enemies per room: numerous weak early waves that
ramp to denser, elite-heavy later ones.

**User request (verbatim intent):** "Needs more monsters in each level too, first few waves can be easier
but have more enemies. Maybe slightly larger maps that move around with the player instead of everything
being in one view."

**In scope:** camera follow + transform, world-space input, bridge alignment, culling, off-screen
indicators, per-room arena sizes, layout/hazard scaling, wave composition/density/spawn distribution,
ranged-enemy engage range, headless + headless-Chrome verification.

**Out of scope / deferred:** minimap (deferred), gamepad aim indicator (Phase 05.2), new environment art for
large arenas (Phase 05.4 — this phase only exposes the world rect), pathfinding, music (05.3).
</domain>

<decisions>
## Implementation Decisions (locked)

### World / arena model
- **D-01:** Arena top-left stays fixed at world `(50, 84)` (`DATA.ARENA.origin`); only `w/h` change per room kind.
  `DATA.ARENA.sizes = { combat:{w:2240,h:1300}, boss:{w:1600,h:960}, rest:{w:1180,h:580} }`.
  `DATA.ARENA.pad = { l:50, r:50, t:84, b:56 }` (wall/HUD framing around the arena).
- **D-02:** `ROOMS.setArena(kind)` mutates `GAME.arena` **in place** (`Object.assign`) so any code/test holding
  `const A = GAME.arena` keeps a live reference. Called at the top of `ROOMS.enterRoom` before the player is placed:
  `'boss'` for boss rooms, `'rest'` for sarovar/kubera, `'combat'` otherwise. `GAME.arena`'s initial literal stays
  the legacy rect (== rest size), so the hub and any pre-room code are unchanged.
- **D-03:** `ROOMS.worldRect()` = `CAMERA.worldRectFor(GAME.arena, DATA.ARENA.pad)` =
  `{ x: A.x - pad.l, y: A.y - pad.t, w: A.w + pad.l + pad.r, h: A.h + pad.t + pad.b }`.
  For a rest arena this is exactly `{0,0,1280,720}`; for combat `{0,0,2340,1440}` (fits 05.4's 2400x1440 art budget).
- **D-04:** Player spawn (left-center) and door positions (right edge, fractional y) keep their existing
  arena-relative formulas — traversing the room toward the gates is part of the larger-map feel; off-screen door
  indicators (CAM-06) + coin vacuum (WAVE-04) keep the post-clear walk readable.

### Camera math (single source of truth — renderer.js)
- **D-05:** New CAMERA state: `sx, sy` (world coordinate of the view's top-left, pre-shake, zoom 1),
  `tx, ty, tz` (last full transform: **screen = world * tz + (tx, ty)**), `VW = 1280`, `VH = 720`.
  Existing `x, y` fields become unused legacy (leave them at 0; do not repurpose).
- **D-06:** Transform (derivation: the punch focus world point F must stay at its un-zoomed screen position F − S):
  ```
  screen = z * (world − F) + (F − S) + k
  tz = z                                   (CAMERA.zoom, the kill-punch pulse)
  tx = F.x − z*F.x − S.x + k.x             (F = fx,fy ; S = sx,sy ; k = kick*shakeScale + shake jitter)
  ty = F.y − z*F.y − S.y + k.y
  inverse: world = (screen − t) / tz
  ```
  With S = 0 this reduces exactly to the Phase 3 `begin()` formula (regression-safe).
- **D-07:** Scroll clamp per axis against the world rect R: `lo = R.x`, `hi = R.x + R.w − VW`;
  if `lo > hi` (world smaller than view) center it: `(lo + hi) / 2`, else `clamp(desired, lo, hi)`.
  Rest arena ⇒ lo = hi = 0 ⇒ identity transform.
- **D-08:** Follow: target = player + look-ahead; look-ahead = `clampLen((aimWorld − P) * LOOK_AIM, LOOK_AIM_MAX)` +
  `moveDir * LOOK_MOVE` (tunables in `CAMERA.CFG`: `FOLLOW_RATE 7`, `LOOK_AIM 0.2`, `LOOK_AIM_MAX 110`,
  `LOOK_MOVE 40`, `SNAP_DIST 900`, `CULL_MARGIN 48`). Desired scroll = target − anchor, anchor = playfield center on screen
  `(VW/2, (pad.t + VH − pad.b)/2)` = (640, 374). Smoothing `S += (D − S) * (1 − exp(−FOLLOW_RATE * dt))`, snap if
  `|D − S| > SNAP_DIST`. `CAMERA.follow(dt)` runs every real frame in `GAME.frame()` (real dt, like `CAMERA.update`);
  in the hub or with no player it snaps to identity (S = 0). `CAMERA.snap()` is called by `ROOMS.enterRoom` after the
  player is placed so room changes never swoop.
- **D-09:** CAMERA reads `GAME`, `DATA.ARENA`, `INPUT` at call time (D-06 Phase 1 pattern) with safe fallbacks, so
  load order (renderer.js before data.js/game.js) is irrelevant.

### Bridge alignment (CAM-03)
- **D-10:** Keep the 1280x720 viewport-sized bridge canvas. Each frame: `SPRITES.clearBridge()` clears in identity,
  `CAMERA.begin()` computes `tx/ty/tz` (always — headless too) and, when Pixi exists, sets
  `worldContainer.position=(tx,ty)`, `scale=tz`, and **counter-transforms the bridge sprite inside worldContainer**:
  `bridgeSprite.position = screenToWorld(0,0) = (−tx/tz, −ty/tz)`, `bridgeSprite.scale = 1/tz`. Then
  `CAMERA.applyCtx(ctx)` does `ctx.setTransform(tz,0,0,tz,tx,ty)` so primitives are drawn in world coordinates.
  Proof: canvas pixel c = tz*W + t; bridge sprite maps c → world `−t/tz + c/tz` = W; worldContainer maps W → tz*W + t = c.
  Net identity pixel mapping and identical screen position for Pixi children and bridge primitives.
  Chosen over moving the bridge to a separate stage layer because it preserves the existing z-order
  (bgSprite → bridge → bgContainer/under-particles → entities → fx) with zero container restructuring.
- **D-11:** Background art: `SPRITES.coverFit(texW, texH, rect)` (pure) and `setBackground(key, rect)` cover-fit the
  world rect expanded by 30px (shake margin). For a rest arena the rect is (−30,−30,1340,780) — identical to today.
- **D-12:** Outer dim/primitive fill in `renderBackground` fills `CAMERA.viewRect(40)` (world coords) instead of the
  fixed screen rect. HUD bridge, screen flash, debug overlay stay screen-space and untouched.

### Input (CAM-04)
- **D-13:** `INPUT.wx, INPUT.wy` (world aim target, init 640/360). `INPUT.mx/my` remain **screen** coordinates from the
  mouse handler. `GAME.syncAim()` (called in `frame()` after `PAD.poll()`, before `update`) sets
  `wx/wy = CAMERA.screenToWorld(mx, my)` when `INPUT.device !== 'pad'`, using the transform actually on screen last frame.
- **D-14:** Gamepad: `PAD` keeps `_aimAng`; right stick above deadzone updates it; while `INPUT.device === 'pad'` and a
  player exists, `wx/wy = player + (cos,sin)(_aimAng) * AIM_REACH`. PAD no longer writes `mx/my`. (05.2 builds the
  aim indicator.)
- **D-15:** `Player.update` aims at `I.wx/I.wy`. Crosshair: kbm → `(mx,my)`; pad → `CAMERA.worldToScreen(wx,wy)`.

### Culling + indicators (CAM-05/06)
- **D-16:** Pure helpers in renderer.js: `viewRect(margin)`, `visible(x,y,r,margin)`, `visibleRect(x,y,w,h,margin)`,
  `edgePoint(wx,wy,inset)`, `clusterIndicators(items, opts)`. Culled enemy sprites stay tracked via
  `SPRITES.cullEntity(e)` (marks seen + hides sprite/marker/weapon) so mark-and-sweep does not destroy/recreate them;
  `drawEntity` re-sets `visible = true`.
- **D-17:** Indicators drawn on the HUD bridge (screen space) after the HUD panels, inset `{l:28, r:28, t:96, b:64}`
  (clears HP panel/title and boss bar), 16 angular sectors, max 8 arrows, doors always first, boss next, then nearest.

### Waves (WAVE-01..04)
- **D-18:** `DATA.WAVES` global tunables: `maxAlive 26`, `weak {hp:0.5, dmg:0.6, cost:0.5}`, `nextWaveAt 0.3`,
  `waveDelay 0.7`, `dripEvery 0.35`, `dripBatch 3`, `spawnMin 360`, `spawnMax 950`, `packSize [3,6]`, `packJitter 70`,
  `engageRange 640`, `eliteCost 3`.
- **D-19:** Per-biome `waves` block on each `DATA.BIOMES` entry (legacy `budget` kept for the numeric `spawnWave(n)` path):
  | biome | count | perWave | fodder | fodderShare | eliteShare |
  |---|---|---|---|---|---|
  | naraka | [3,3] | [4,9] | ['preta'] | [0.85,0.35] | [0,0.15] |
  | patala | [3,4] | [6,11] | ['preta','rakshasa'] | [0.7,0.3] | [0.1,0.3] |
  | ranabhoomi | [3,4] | [8,14] | ['preta','rakshasa'] | [0.6,0.25] | [0.2,0.45] |
  | vaitarani | [4,4] | [10,15] | ['preta'] | [0.45,0.25] | [0.3,0.45] |
  Values lerp by `roomFrac = (roomIdx−1)/(rooms−1)`. Fodder are **weakened** instances (`Enemy(..., mods)`), not new
  enemy types. Preta (hungry ghost) as fodder in every realm is mythologically consistent; no gods as enemies.
- **D-20:** `GAME.waves` becomes an array of unit lists (`[{id, weak}]`); `ROOMS.spawnWave(x)` still accepts a number
  (legacy budget path used by existing tests) or a unit list.
- **D-21:** Room-clear condition: no alive enemies AND `GAME.waves` empty AND `GAME.spawnQueue` empty.

<risks>
## Risks
1. **Transform drift between Pixi and bridge** (highest): mitigated by one stored transform (`tx/ty/tz`) consumed by
   both paths, a headless algebraic alignment test (05.1-02) and an in-browser `toGlobal` numeric check + screenshots (05.1-04).
2. **Hidden screen-space assumptions**: `fillRect(-30,-30,W+60,H+60)`, setBackground's 1340x780 rect, VFX stress/ambient
   rects, crosshair. All enumerated in plans; grep gate for `1280|720|this.W|this.H` inside world passes.
3. **Smoke flakiness / run length**: denser waves increase frames per room; plans require printing frame counts and
   keeping god-mode victory under 70% of the 300000-frame cap; weak-player death path must still die.
4. **Perf**: 26 alive enemies + particles in a 2240x1300 world — culling (05.1-04) + alive cap; FPS reported by the
   browser check (headless SwiftShader FPS is indicative only).
5. **Feel**: follow rate / look-ahead / wave numbers need a human playtest — all tunables live in `CAMERA.CFG`,
   `DATA.ARENA`, `DATA.WAVES`, `DATA.BIOMES[].waves`.
6. **Parallel phases**: 05.3/05.5 may edit ui.js/audio.js/index.html concurrently — this phase must not touch them;
   the hub reset of the camera is done in CAMERA.follow (reads `GAME.state === 'hub'`), not in ui.js.
</risks>
